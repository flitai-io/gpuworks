# 多机推理

**适用场景**：模型单节点放不下，或希望把 TP / PP 拆到多台节点上，让一个部署的多个 rank 分布在多台机器。

完成后，一个副本的所有 rank 就绪，并能通过部署的服务名完成一次推理请求。

**前置条件**：

- 至少两个在线节点，已按[接入节点](connect-nodes.md)接入。
- 所有节点需共用一个参数网络；没有共用参数网络时，只有全部节点都允许管理网承担参数同步，才能回退使用管理网。选网与 RDMA 设置见[配置节点网络](configure-networks.md)。
- NVIDIA 使用主机 RDMA 参数网络时，通过 NCCL/UCX 通信；该网络不能用在 runveil（udocker driver）节点上。
- 昇腾多机必须使用加速器 RDMA 或加速器 HCCS 网络。
- 已熟悉单机部署流程，见[部署模型、选卡与解释调度结果](deploy-models.md)。

## 部署一个多机副本

1. 核对所选网络的各节点地址，并确认这些地址之间的防火墙允许双向 TCP。
   使用管理网时，地址是节点连接 server 所用的本机地址；昇腾节点还需验证实际选用的加速卡能互通。
   需要验证链路时，按[网络内部测试](configure-networks.md#内部测试)选择这些节点进行测试；
   TCP 可达不代表 RDMA 或加速卡网络可用，应选择相应的测试方式。
   网络探测失败时，先修正路由、防火墙或端口，不要通过关闭认证绕过。
2. 选择放置方式（见[自动放置与手动放置](#自动放置与手动放置)）。手动时在部署页按 rank 0…N-1 固定节点顺序；自动时可以只写前几个 rank 的节点，其余由平台选。并设置并行方式：张量并行（TP）和流水线并行（PP）
   都是整个部署的值，总卡数 = TP × PP，每个节点运行 TP × PP ÷ 节点数 张卡（必须整除）。
   选好节点后默认 TP = 所选节点中最少的 GPU 数、PP = 节点数；TP 也可以跨节点，例如两台各
   1 张卡的节点用 TP 2。GPU 多于每节点卡数的节点只用其中一部分。
   多机表单的并行度位于节点之后、镜像之前；TP / PP 错误会标在对应字段上，不会阻止镜像和权重获取预估显示。
   自动放置必须写 TP：平台要靠它算出每台节点需要多少张空闲卡，缺 TP 时返回 400 `AUTO_PLACEMENT_TP_REQUIRED`。
3. 选择镜像和权重，展开逐节点的获取预估，例如「2 个节点中 1 个需要拉取镜像」。
   需要获取的节点按[拉取设置](configure-pull-settings.md)处理，已有资源的节点跳过；启动前预拉取镜像也使用同一份候选。
4. 检查表单的配置评估，修正节点、共用网络和 TP / PP 的错误，并确认 master 端口可用。
   表单预检查只校验配置与节点条件，不发起网络连通性或带宽测量。
   使用 API 独立探测时可调用 `POST /api/v1/deployments/preflight`；只有请求中开启
   `bandwidth` 才测 TCP 带宽，字段和结果见 [API 参考](../reference/api.md)。
5. 在命令预览中核对节点顺序和并行度后提交部署：vLLM 对应 `--tensor-parallel-size` / `--pipeline-parallel-size`，
   SGLang 对应 `--tp-size` / `--pp-size`；PP 大于 1 时才注入对应 PP 参数。rank 0 的地址作为 master，对外流量只进入 rank 0；
   其余 rank 是协同工作的 follower，无需逐个调用其接口。
6. 在部署详情等待全部 rank 就绪，再通过该部署的服务名在 Playground 或 `/v1` 发起一次请求。
   只看到 rank 0 创建或开始加载不代表整个副本已经可用；失败时查看对应 rank 的事件和日志。

需要手写启动命令时，在命令预览点「编辑命令文本」：编辑框从服务端生成的脚本开始，所有 rank 共用这一段脚本，
`${GPUWORKS_NODE_RANK}`、`${GPUWORKS_HEADLESS}`、`${GPUWORKS_MASTER_ADDR}` 等变量在每个 rank 启动前替换成该 rank 的值，
编辑框下方逐 rank 展示替换后的结果。命令必须引用 `${GPUWORKS_NODE_RANK}` 或 `${GPUWORKS_HEADLESS}`，否则评估与创建返回
`MANUAL_COMMAND_RANK_BLIND`。详见[多机与 PD 的手工命令](../explanation/launch-config.md#多机与-pd-的手工命令)。

如果部署一直等待节点，查看时间线中的 `DEPLOYMENT_UNSCHEDULABLE`：它列出放不下的 rank、节点和原因。
一个副本的全部 rank 必须同时满足模型、镜像、端口、GPU 与显存条件，才会一起创建；
不会先让 leader 占卡，也不消耗副本重试次数。按原因补齐资源后平台自动继续。PD 部署的多机单元同样如此。

完整创建字段见 [API 参考](../reference/api.md)。

## 自动放置与手动放置

多机部署和单机一样有两种放置方式：

| 方式 | 谁选节点 | 怎样用 |
|---|---|---|
| **自动** | 平台。请求没写的 rank 在创建时由平台按空闲卡挑；副本启动时发现节点放不下，只把放不下的 rank 换到别处 | `placement_mode: "auto"`，必须有 `placement.tp`；`node_uuids` 可以不写，也可以只写前几个 rank（其余补在同一张网、同一种架构里） |
| **手动** | 你。每个 rank 的节点都由你写，平台不替你改 | 省略 `placement_mode`（按手动），写满 `nnodes` 个 `node_uuids` |

升级前已有的多机部署都是手动。部署详情的 `placement_mode` 给出当前方式；用 `PUT /api/v1/deployments/{id}/placement-mode` 可以在两者之间切换，不重启实例，见[部署模型](deploy-models.md#部署后调整)。

### 创建时怎样挑节点

平台为每个副本在满足下面条件的节点里挑 `nnodes` 台，一个副本内的节点必须同一张计算网络、同一种 GPU 架构：

- 在线、可调度（没有停止调度或驱逐）、满足部署的节点条件，并有放下一个 rank 所需的空闲卡（TP × PP ÷ 节点数）。

满足条件的组按下面的顺序比较：

1. RDMA 网络（主机 RDMA 或加速器 RDMA）优先于以太网。
2. 已有该模型文件的节点多的组优先。
3. 组内按放置策略：多机默认 `binpack`，选空闲卡最少但够用的节点，让整台空节点留给下一个部署；`spread` 选空闲卡最多的。已有模型的节点总是排在前面，卡数相同按节点编号定，同样的输入得到同样的结果。

挑好后，请求就像你自己写了这些节点一样走一遍常规检查，部署保存的是挑中的节点，节点和卡的占用以启动时的调度为准。评估接口（`POST /api/v1/evaluate`）对自动放置的多机请求返回 `auto_placed: true`，预览显示此刻会挑中的节点，创建时重新挑一次，两次可能不同。

没有任何一组放得下时，创建返回 409 `UNIT_PLACEMENT_NONE`，参数写明各项检查排除了多少台节点（不满足节点条件、已停止调度、离线、空闲卡不够、没有计算网络）以及最大的一组有几台；评估则把它作为 `placement_mode` 字段的错误。

### 副本启动时的重新挑选

挑中的节点就是单元（副本）里写着的节点，之后的匹配、网络解析、节点失联重调度和驱逐都照常按它们工作。副本需要启动而没有实例时，平台再用当前的空闲卡试算一次：

- 它的节点都在线且放得下：照原样启动。
- 某些 rank 的节点已停止调度、不再满足节点条件，或者启动会被拒绝（卡被其他部署占了）：**只把这些 rank 换到别的节点**，其余 rank 保持原节点，选法与[节点失联重调度的选法](node-failover.md#怎样选替换节点)相同（同计算网络、同厂商和架构、卡空闲、试算放得下）；一个 rank 一个 rank 换不出时，再整组重新选。换完在时间线记 `UNIT_PLACED`：第几个副本、原节点、新节点和原因（`reason`，例如 `node_cordoned`、`placement_rejected` 或调度器的拒绝码）。
- 没有地方可去：副本保留原来的节点，继续等待，时间线照常给出调度器的等待原因；平台每分钟再找一次。
- 节点离线属于[节点失联重调度](node-failover.md)，仍按它的等待时间处理；被驱逐的节点上的副本按驱逐的先起后切处理。这两种情况自动与手动部署一样。
- 同一部署自己的实例还在离开这些节点（重启、退役）时不重选，它们的卡马上释放。

手动部署不做这件事：节点放不下时副本一直等待，原因写在 `DEPLOYMENT_UNSCHEDULABLE`。想让平台换，切成自动。

## 为已有部署增加副本

**自动放置的部署**只说要几个副本：

1. 在部署详情打开**调整副本**，填副本数；需要的话，在**首次放置节点**里写新副本的节点。
2. API 是 `PUT /api/v1/deployments/{id}/replicas`，请求 `{"replicas": 3, "place_on": ["<节点 UUID>", …], "remove": ["<实例 UUID>"]}`：
   - `place_on` 按顺序给新副本的 rank 指定节点：先是第一个新副本的 rank 0…N-1，再是下一个的。可以只给一部分，没写的由平台在同一张网里补；多于新增副本的 rank 总数返回 400 `REPLICAS_PLACE_ON_TOO_MANY`，写的节点凑不成一个能放下的副本返回 409 `REPLICAS_PLACE_ON_REFUSED`（`params.reason` 为 `no_group`）。
   - 没有任何一组放得下返回 409 `UNIT_PLACEMENT_NONE`。
   - 缩小副本数时，`remove` 里的实例所在的副本先去掉，不写则去掉最后加入的。

   新副本的 leader 不与已有副本的 leader 在同一台。`place_on` 只管新副本第一次放在哪里，之后与其他副本一样参与启动时的重新挑选。

**手动放置的部署**提交完整的副本列表（`units`），用推荐按钮可以省事：

1. 在部署详情打开**调整副本**，点击**添加推荐副本**。
2. 核对填入的节点列表，确认无误再保存。没有推荐组时，先查看各类节点被排除的数量，按原因补齐条件后再选择节点。

推荐组中的节点须在线、可调度、满足节点条件，并共享同一计算网络和 GPU 架构；每个节点需有一个 rank 的空闲卡。
平台按部署配置逐 rank 试算后填入列表，leader 不与其他副本的 leader 同节点。推荐只是建议，需要你确认后才保存；它与自动放置用的是同一套挑选，区别只是结果由你确认。手动部署的 `place_on` 返回 400 `REPLICAS_BODY_SHAPE`。

**节点失联或被驱逐时**，自动和手动部署一样：平台会自动重调度，只换出问题的那个 rank，替换节点按同样的规则选（同计算网络、同 GPU 厂商和架构、卡空闲、试算放得下），不消耗重试次数。等待时间、选择规则和撤回见[节点失联重调度](node-failover.md)。

## 限制

- 自动放置只替你选节点，不选卡：每台节点用多少张卡由 TP × PP ÷ 节点数决定，用哪几张由调度器在启动时挑。多机副本不能钉卡。
- 平台按计算网络的**声明**判断能否连通，不用网络测试结果；声明与实际不符（例如交换机不通）时仍会挑出不通的组，启动后由引擎报错暴露。选网与验证见[配置节点网络](configure-networks.md)。
- 自动放置不会为了凑齐一组而先起一部分 rank：一个副本的 rank 要么一起创建，要么一起等。
