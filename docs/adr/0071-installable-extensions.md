# ADR 0071: 可安装扩展：通用核心 + 签名插件包

日期：2026-11-17 · 状态：已接受；部分取代 [ADR 0070](0070-extension-tiers-and-edition-boundary.md)（决策 1、10 被取代，其余保留并按本页扩充）。本页的决定部分已实现，见「实施状态」。

术语以 `CONTEXT.md` 为准：**插件包**、**发布者证书**、**推送表**、**权威**、**宽限**、**限制覆盖**、**extclock**、**扩展模块**、**功能键**、**可用性**。

## 背景

ADR 0070 设想由另一个 Go 模块把带额外能力的代码编进 server，生成单独构建的二进制。各个部署要的能力并不相同（自定义角色、身份对接、审计外送、KMS、控制台品牌、站点自己的可用性规则……），为每种组合出一个构建，意味着多个二进制、按版本名分开的发布索引和「换版本」的升级路径；客户也无法只装自己要的那几项。

另有几条约束一起决定了做法：server 与 agent 都是 `CGO_ENABLED=0` 的静态二进制，Linux 与 macOS 都要支持，所以没有 Go `plugin`、没有 dlopen；规模目标是 1000 节点 / 3000 实例 / 网关约 2k QPS，热路径上不能等任何进程外调用；数据库只有一个写连接；许多站点离线、多年不升级；插件掉线时要继续执行最后的限制，运行中的工作不能停，本地管理员必须总能登录。

## 决策

1. **分层（取代 ADR 0070 决策 1）。**

   | 层 | 运行在 | 谁写 | 放什么 |
   |---|---|---|---|
   | T0 核心 | server、agent | 开源 | 全部通用能力与每个执行点（路由权限、数据范围、配额与预算计数、可用性、节点上限、调度保持、放置过滤）、通用执行器、插件宿主、HA。按定义免费 |
   | T1 内置模块 | server 进程内 | 仅开源 | 经 `app.Module` / `app.Host` 的核心内部组合，插件宿主本身就是一个内置模块。`cli.Options.Extensions` 留给测试与分叉，不是厂商或第三方的分发途径 |
   | T2 包的服务端部分 | server 的子进程 | 任何受信任的发布者 | 需要 I/O、状态、流程或对接的决定：可用性权威、自定义角色、身份对接、计费、审计外送、KMS、品牌、配额与资源池编辑、云厂商驱动 |
   | T3 包的节点部分 | 节点上的核心工作负载与作业 | 任何受信任的发布者 | 用 GPU 的产品（微调、Notebook、评测、第三方应用）；agent 里不跑插件代码 |
   | T4 策略部分 | server 内（WASM） | — | 只预留名字与接口，不实现；将来实现时也永远不进写事务 |

   一个插件包可以同时带 T2、T3 和界面。

2. **什么免费由代码决定。** 编进开源 server 的就是免费的。框架只有机制（可用性、上限、保持、计数、角色、范围、资源池），不点名任何功能，没有受控功能清单；核心代码里的功能键字面量以棘轮预算保持为 0，与 `edition_branches = 0` 并列。功能键是否受控由插件包在自己的清单里声明（`gate`）：`none` 永远完整，`self` 由声明它的包自己作答，`authority` 只由发布者证书指定的权威包作答，没有权威包时为锁定（`FEATURE_PROVIDER_ABSENT`），声明为隐藏呈现的则隐藏。命名空间写在键里：项目发布者用无前缀的键，第三方用 `acme.x` 或 `acme.x.y`，符合 `featuregate.Key` 已有的三段文法，`featuregate.Source` 不变。

3. **所有热路径上的判断点都在核心。** 逐请求、逐插入、逐状态上报、逐认领、逐放置的判断都是核心里的执行器，从插件推来的表作答：一次原子读加 O(1) 查表，放行路径零分配。功能需要一种新的判断点时，核心增加一种新的表，且这种表必须对社区版也有用；表的目录就是核心对外的扩展接口，只随核心版本增加。只有两处同步调用插件：登录时校验密码（LDAP），以及开机后第一次解密凭据（KMS 解包数据密钥），都不在请求、插入、上报、认领或放置路径上。

4. **一种包格式。** 插件包 `.gwpkg` 是签名的 tar，最多四个可选部分：服务端进程（每个 os/arch 一个静态可执行文件）、节点组件（作为核心工作负载运行的服务与 GPU 作业模板）、界面包、插件自带的存储迁移。清单按核心认识的 schema 严格解码，列出每个成员文件的大小与 SHA-256，以及包可能产生的全部码，每个码带 en/zh 文案（ADR 0067）。云厂商驱动与第三方应用用同一种格式。

5. **信任链。** 两把离线保管的项目根密钥编进核心，签发**发布者证书**；证书写明授予的权限：可签的包名前缀、可声明的功能命名空间、该命名空间唯一的权威包（`authority_id`）、可声明的特权角色、可推的特权表、能否提供同源界面模块、最低隔离级别。
   - 证书的 `not_after` 只限制签发窗口：在窗口内签出的包永久有效，已安装的包永不过期。
   - 根密钥签名的信任更新（增减根、吊销、最低版本）可以离线导入，按序号防重放。
   - 第三方发布者由主机 root 写在 `server.yaml` 里信任，默认没有特权角色和特权表、界面只能用 iframe、必须有 Landlock；主机信任的发布者可以作为权威，但只能经 root 显式编辑 `server.yaml`，只限它自己的命名空间，永不用于无前缀的键。
   - 吊销的包拒绝安装；已安装的包不会因吊销被自动停止，它推的授权也不释放，只显示横幅由管理员决定。唯一例外是按摘要精确吊销的权威包：启动时不再运行，按掉线处理（先宽限再降级）。
   - 权威包有防回滚的最低版本：一个版本健康运行 24 小时后成为最低版本，根签名的信任更新也可以抬高它；低于它的安装、升级与回滚都被拒绝。
   - 开发模式（`serve --plugin-dev`）可以加载未签名的包，常驻横幅，数据目录带生产标记时拒绝进入。
   - 校验失败即拒绝，全部步骤通过之前不解包到位；安装、每次启动、每次拉起进程前都校验。

6. **进程模型。** 插件是 server 的子进程，经自重入跳板 `gpuworks plugin-exec` 拉起：跳板在 `execve` 之前施加 `no_new_privs`、Landlock、rlimit、cgroup 与 Pdeathsig（拉起它的线程锁定在 OS 线程上），沙箱由宿主施加，而不是信任插件自己施加。默认与 server 同一个用户；每插件独立用户是之后的加固。没有 Landlock 的主机（4.19 内核的麒麟 V10、UOS 20、macOS）上，第三方包默认拒绝，除非证书写明 `min_isolation: none` 或 root 在 `server.yaml` 逐包放行，控制台标明「仅签名保护」。插件永不以 root 运行；需要 root 的主机步骤只能来自封闭的 `host_setup` 词汇，由核心的 `gpuworks install` 执行，不运行脚本。

7. **协议 `gwx/1`，主版本冻结。** 两对继承的 socketpair，各跑一条明文 HTTP/2：fd 3 上插件提供生命周期调用、服务调用与被代理的路由，fd 4 上核心提供宿主接口。fd 就是身份：不存在可被别的进程连接或抢占的 socket 路径，推送不带任何可伪造的身份字段。错误是 ADR 0067 的码加参数。
   - 主版本 1 冻结：信封、握手、错误形状、推送信封都不再变；改主版本需要新的 ADR，支持主版本 2 的核心仍至少保留主版本 1 三年。
   - 增长只经能力：每种能力独立带版本，发过的版本在主版本 1 内永不移除，旧版本由小适配器转成核心的规范形式。
   - 行严格解码：任何改变执行结果的字段都是新的 schema 版本，旧核心不会悄悄丢掉一条限制；只用于显示的可选数据放在指定的 `display` 子对象里，旧核心可以丢弃。
   - 兼容性在安装时由签名清单静态判定（清单的 `Requires` 必须是本核心提供的能力的子集），离线管理员上传时就能看到结论。

8. **推送表。** 插件不进热路径，只把决定推成带类型的表；核心校验、持久化，再原子替换一个快照指针。
   - 四个类别：限制（Restrict，按交集合并，任何获准的插件都能推，永不失效）、授权（Grant，只接受该命名空间权威推的行，权威按 fd 认定；插件掉线超过宽限即降级）、显示（Display，横幅与品牌，从不参与执行）、不透明（Opaque，证明材料，只存储与转交）。
   - 合并只会收紧：保持取并集，上限、配额与容量取最小，准入保持取并集，额度要求每个所有者都放行，约束取并集；授权按键独占或按角色键取并集、冲突即拒绝。装一个插件永远放不松另一个插件的限制。
   - 写入：每个 tick（至多 1 Hz）把所有所有者的待写推送放进一个写事务，大表只写核心算出的差量；持久化成功后才替换快照，一次 tick 涉及的多种表不会被看到一半。
   - 持久化用带类型的表：每种小表一张表、`body` 列只放一个具名 Go 类型（核心的规范形式，而不是插件的线上 schema），大表用带类型的行（ADR 0032）。行引用核心 id，不引用名字。
   - 启动时在路由构建之前读入全部推送表并生效，所以核心重启后、任何插件进程起来之前就按最后的状态执行。已安装但不再通过校验的包（文件损坏、按摘要吊销、可执行文件缺失），限制与显示继续执行，只丢弃它的授权行：删除或损坏包文件永远不会放松限制，只有经审计的卸载或覆盖才会。

9. **掉线、宽限、时间线与 extclock。**
   - 插件掉线（`running`/`degraded` 以外的任何状态，含停用）时，它自己的路由立即回 503；限制按推送的继续执行，无限期；授权在**宽限**之后降为 `min(当前, down_access)`（默认只读），带码 `PLUGIN_UNAVAILABLE`。
   - 宽限由所有者随表推送，核心限定在 60 秒到 24 小时，没给时为 1 小时；站点只能调低（`server.yaml` 的 `plugins.policy.max_down_grace`）。掉线起点持久化，重启不续期；每段掉线另有一次 2 分钟的启动延长，从持久化的起点算，server 或插件重启都不叠加；插件进程声明自己已就绪（`$/ready`）后，它之后的掉线不再有启动延长。
   - 时间线：表的行可以带将来的步骤（例如「现在完整；T1 显示宽限提醒；T2 起只读」）。核心对全部快照里最早的下一步只设一个计时器，到点重算并替换快照，热路径从不比较时间；插件死了步骤照常生效，所以杀掉插件不能延长到期。
   - **extclock** = `max(墙钟, 高水位)`：高水位每分钟和关机时持久化，运行中按单调时钟前进，回拨墙钟不能让已过的步骤复活。时钟被拨快的离线站点有两条纠正途径：root 在 server 停止时执行 `gpuworks plugin clock reset --to <时间>`（只写离线维护日志，下次启动时在任何插件起来之前经运行中的同一条校正路径应用、审计并显示横幅，运行中的 server 无从覆盖），或持有根授予的 `clock_authority` 角色的包提交它已验证的纠正；单次纠正不超过 366 天，审计并显示管理员横幅。核心只拥有单调规则，可信时间的其余部分（节点时钟互证、硬件钥匙时钟）留在插件里。
   - 停用等同掉线，不等同移除；只有卸载（先给影响预览、显式确认）才释放上限与保持。

10. **限制覆盖。** 插件死了而它推的某条限制必须解除时，管理员可以覆盖一条限制类条目：只能放松（删除一个保持、调高一个配额、补一次额度），持久化、审计、显示在插件状态里；它绑定所有者的表版本，所有者再次推送同一条目即被取代（所有者活着并重新做了决定），并提示管理员。离线时用 `gpuworks plugin pstate clear <id> <表>` 释放整张限制表（授权不行），同样经离线维护日志在下次启动时应用。这是核心代码，免费。

11. **本地管理员兜底。** `users.local_admin` 为真的用户在恢复面（登录、`reset-password`、`/api/v1/plugins/*`、覆盖、恢复所需的设置）上不受推送的约束、准入保持与推送角色影响，执行器先查这个标记。插件管理接口是核心路由：`platform_admin` + 管理员会话、从不受功能门控、全部审计、不对 AI 助手与 MCP 开放。所有插件掉线、被移除或崩溃循环时，本地管理员仍能登录并管理插件。

12. **扩展路由前缀 `/api/v1/x/<名>/`。** 编译进来的模块与插件包的管理路由都挂在这棵子树下，核心永不在 `/api/v1/x/` 下注册路由，所以扩展名可以与核心路径段同名，也不会与核心将来新增的路径冲突（对多年不升级的站点尤其重要）。插件的路由在签名清单里静态声明（方法、模式、动作、访问级别、功能或明确不受门控、读者是否可读等）；「每条路由要么指明功能、要么标为社区路由」从构建时规则变为安装时规则。核心先做认证、动作授权、功能门控、请求体上限与审计，再经 fd 3 转发；插件看不到会话，主体信息由核心签名后放在请求头里。

13. **运行中的工作永不中断**（扩充 ADR 0070 决策 9）：推送状态、插件崩溃、宽限降级、吊销与卸载都只作用于新的请求、写入与准入，从不停止、驱逐或重启正在运行的负载；效果只限于停止调度（从不驱逐）、拒绝新写入与拒绝新准入。

14. **KMS 只包裹凭据数据密钥。** master key 还派生登录会话的签名密钥与安装标识，不能交给插件或外部 KMS；KMS 插件只包裹与解包凭据加密用的数据密钥（开机后第一次解密时一次同步调用）。KMS 插件自己的密文设置用另一把由 master key 派生的密钥封装，否则它读不到自己的凭据。

15. **国密不是插件。** 现在由外部 TLS 终结器提供；客户合同需要原生 TLCP 或 SM4 落盘时，SM 原语进核心（免费）。不做在公网端口上接管监听的插件。

16. **核心降级只检测兼容性，不做降级迁移。** 推送状态与插件数据带版本标记；核心启动时发现比自己新的版本，就以带码错误拒绝启动并说明需要哪个版本，不丢执行、不改写数据；提供只读的 `gpuworks plugin compat` 供降级前检查。这与 `namespace_migrations` 已有的 `ErrNamespaceTooNew` 行为一致。

17. **一个 server 二进制（取代 ADR 0070 决策 10）。** 官方构建传 `cli.Options` 的零值，二进制永远是社区版（版本名只用于显示）。按版本名分开的发布索引、`--allow-edition-change`、`SERVER_EDITION_MISMATCH` 与「换版本」的安装路径退出官方发布流程：从现在起不再扩展，第一个可用性权威作为插件运行之后由一次清理删除；`cli.Options` 的其余入口留给分叉。

18. **HA 只在核心。** 插件只在主节点运行，插件的 SQLite 存储由核心 HA 复制。

19. **其余已确认的产品决定。**
    - 第一个插件包是可用性权威，之后的权威包以它为参照：它的掉线宽限在决策 9 的范围内选定，存储与 HA 方式和其他包一样在清单里声明。
    - 审计防篡改：核心在写入时做哈希链（每行约 1 µs）；保留期、签名与外送 SIEM 由插件负责。
    - OEM：只做控制台品牌（推送的 `branding` 表）；改二进制、安装器与 agent 名称是经 `cli.Options` 的定制分叉。
    - LDAP 不做离线校验缓存：LDAP 掉线时本地用户与已有会话照常。
    - 离线站点另出一个带官方插件包的发布压缩包，默认下载保持小；默认不安装任何插件。
    - WASM 策略部分只预留，满足条件（推送表表达不了的请求期逻辑，最可能是网关内容策略）时再做。

20. **`server.yaml` 增加 `plugins:` 键**（扩充 ADR 0070 决策 7），由 root 拥有：信任的发布者、站点策略（只能收窄）、无沙箱放行清单、要求的隔离级别、最长掉线宽限、游标最大滞后。插件包永不使用 `extensions:`、`namespace_migrations` 与 `ee_` 前缀；推送表与插件管理用的表是核心迁移建立的核心表。

21. **契约测试。** 在 `internal/testenv/extmodule` 之外增加对假插件进程的契约测试，覆盖：热路径零等待零分配、写事务里的钩子不调 Store 与插件、框架不点名功能、限制按交集合并与授权只来自权威、启动即执行、运行中的工作不受影响、本地管理员兜底、插件只引用公开包、只运行受信任的包、行严格解码、能力版本永不移除，以及没有安装任何包时路由清单、控制台清单与全部钩子与社区版逐字节相同。

## ADR 0070 各条决策的去向

| ADR 0070 决策 | 去向 |
|---|---|
| 1 四个层级、T1 承载逐请求的工作 | 被决策 1 取代：T1 只是核心内部组合，逐请求的工作永远是核心执行器 |
| 2 单一入口，零值即社区版 | 保留给测试与分叉；官方构建传零值，`cli.Options` 不是厂商分发途径 |
| 3 开源代码只说可用性 | 保留，词汇扩充为上限、保持、计数、角色、范围与资源池；加上「免费由代码决定、框架不点名功能、包声明 `gate`」（决策 2） |
| 4 服务端决定，界面只渲染 | 保留；加上插件清单的安装时路由规则与 `/api/v1/x/<名>/` 前缀（决策 12） |
| 5 扩展不拿 Store | 对模块保留；插件只引用 `pkg/pluginsdk` 与 `pkg/extapi`，经 `gwx/1` 与自己的存储工作，从不打开核心数据库 |
| 6 扩展迁移单独记录 | 留给分叉；插件不用 |
| 7 `server.yaml` 保留 `extensions:` | 保留；增加 `plugins:`（决策 20） |
| 8 写事务里的钩子是纯函数 | 原样保留；另加：钩子不请求任何重算，WASM 永不进写事务 |
| 9 运行中的负载不被中断 | 保留并扩充到宽限降级、吊销与卸载（决策 13） |

## 取舍

- **子进程 + 推送表 vs 编译进来的模块**：编译模块能在事务里同步决定，但每种能力组合要一个二进制，模块依赖开源内部包、必须跟着开源 master 重新构建。推送表让插件离开热路径，代价是每种新的判断点都要核心加一种表、随核心版本发布；表的目录因此成为必须长期兼容的公开接口。
- **子进程 vs WASM**：WASM 隔离更好，但插件要做 I/O、对接外部系统与持有状态，在 WASM 里都要宿主一个个提供；子进程用现成的语言与库。WASM 只为推送表表达不了的请求期逻辑预留。
- **fd 认身份 vs 带 token 的 socket**：继承的 socketpair 不存在可以被同一用户的别的进程连上或抢占的路径，也绕开 macOS 的 `sun_path` 长度限制；代价是插件只能由核心拉起。
- **掉线后有界宽限 vs 立即降级**：立即降级会让权威插件成为整个集群的单点；无限保持完整又等于杀掉插件就能绕过商业或站点自己的规则。有界、持久化、站点只能调低的宽限加上照常生效的时间线，两头都堵住。
- **吊销不自动停止 vs 立即停止**：离线站点收不到吊销，在线站点立即停止会造成大范围的功能中断；所以吊销只拒绝新安装，旧版本的风险由最低版本与按摘要吊销权威包兜住。
- **降级只检测 vs 降级迁移**：降级迁移要为每种表写并测试反向变换，且可能悄悄丢掉限制；拒绝启动并说明需要的版本，不会丢执行，也不会改坏数据。

## 后果

- 新的扩展需求先问：能否用已有的表表达；不能时，新判断点是一种新的核心表，必须对社区版有用，带契约测试，只随核心版本发布。
- 插件包承担兼容的负担：新的可用性规则、身份编辑、计价规则与修复都只发新包，不需要升级核心；只有新的执行点需要升级核心。
- 现有的单独构建方式（`cli.Options`、扩展迁移、构建时界面叠加）继续对分叉与测试有效，但不是官方或第三方扩展的分发途径。
- 契约与操作细节见 [扩展点](../dev/extensions.md)，线上格式见[插件协议与线上格式](../reference/plugin-protocol.md)。
