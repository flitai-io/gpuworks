# ADR 0058: 调度中心只执行运维事先下达的指令，休眠让出到每实例残留，节点失联重调度按运维改放置的方式进行

日期：2026-10-25 · 状态：已接受

术语以 `CONTEXT.md` 为准：**休眠残留**、**定时计划**、**闲置休眠**、**唤醒等位**、**让位唤醒**、**节点失联重调度**、**驱逐**。
补充 [ADR 0033](0033-replica-level-lifecycle.md)（睡眠意图在实例上）与 [ADR 0029](0029-deployments-reconcile-as-units.md)（部署按副本对账）。

## 背景

sleep / wake 和副本数全靠手动：唤醒放不下只回 409，运维要自己找占卡者、先让它睡、再回来唤醒；多个模型轮流用同一批卡时，
每天要重复同样的操作。节点宕机后，单机副本不会自己换地方，多机副本在同一组节点上重试到耗尽，PD 的单 rank 副本没有离线检测，
驱逐又跳过多机和 PD。同时，休眠按固定 1.5 GiB 计残留，与实际相差很大（小模型约 0.6–1 GiB，多卡大模型约 4 GiB）。

可以往两个方向走：做一个“聪明”的调度器（按负载扩缩、抢占低优先级部署、挂起请求等唤醒、休眠后仍为原部署保留份额），
或者只替运维做运维本来就会做的动作。前者需要优先级、SLA 和公平性的一整套语义，出错时很难解释；后者每个动作都能对应到一条 API 调用。

## 决策

**1. 自动化只执行运维事先下达的指令，经过与 API 相同的生命周期锁和同样的顺序，不抢占、不按负载扩缩。**
定时计划、闲置休眠和唤醒等位是三种“事先下达的指令”：运维写下“周几几点休眠 / 唤醒 / 副本数 N”，设下“闲置多久休眠”，
或在唤醒放不下时选择“等位”。评估器（`internal/server/automation`，15 秒一个 tick，容量释放时也会被唤醒一次）
只读这三类数据，到点调用与 API 同一批领域函数（资格检查、唤醒准入、意图写入），并与 API 共用同一把生命周期锁，
所以定时唤醒和手动唤醒不会同时通过同一张卡的准入。每个自动动作写部署时间线（`AUTO_SLEEP`、`AUTO_WAKE`、`AUTO_SCALE`、
`WAKE_WAITING`、`WAKE_WAIT_TIMEOUT`、`SCHEDULE_ACTION_FAILED`），失败不重试。具体约束：

- 每个时间点只执行一次；server 停机错过的，启动时只补最新的一次，且不得超过 12 小时。手动操作不会在下一个 tick 被改回去。
- 闲置计时从 server 启动、最近一次唤醒、最近一次用户请求中最晚的一个算起；健康检查等平台自发的探测请求不算。
- 唤醒等位只拿现成的空位，30 分钟放弃；等位起点落库，server 重启不丢。
- 让位唤醒（`?yield=true`）是运维点名的一次性动作：先让可休眠的占用者休眠，占用者不可休眠则整体拒绝（409 `WAKE_YIELD_BLOCKED`），什么都不改。
- 定时副本数只用于单机部署；不做抢占、负载自动扩缩、网关挂起请求等唤醒。

持久化：每条计划一行（`lifecycle_schedules`，带类型的列），闲置休眠与重调度等待是部署上的整数列，等位起点是实例上的时间列。

**2. 休眠让出容量，只保留每实例的残留；“休眠仍保留原有分配权”的做法不采用。**
已确认休眠的实例，分配权缩到它的残留，卡上其余显存可以让给别的部署，唤醒时须重新过准入。残留按实例记：
实例独占这几张卡、卡上没有平台外进程时，agent 在休眠成功约 1 秒后读卡的已用显存，作为实测值；否则由 server 按模型参数量分档
（≤3B 0.75 GiB、≤30B 1 GiB、≤200B 1.5 GiB、更大 2.5 GiB）加 CUDA graph 池 0.5 GiB（存储的规格看不出是否 eager，按开启计）、
多卡 +0.5 GiB（8 卡及以上 +1 GiB）估算，限制在 0.75–4 GiB，模型大小未知按 1.5 GiB。没有实测值时用估算，从不当作 0；
读数来自整卡，偏高，方向安全。参数量由权重字节数和已存的精度推出，不新增持久化事实。

配套的两条拒绝，让“让出的容量”不被超卖：L1 休眠前，权重搬进主机内存要放得下可用内存减去余量（总量 5% 与 4 GiB 中较大者），
放不下拒绝并提示 L2，未观测到主机内存时不判断（409 `SLEEP_HOST_MEMORY_INSUFFICIENT`）；唤醒时卡被平台外进程占着则拒绝
（409 `WAKE_GPU_HELD_OUTSIDE`），等位和让位都不能绕过。

被否决的做法是“普通休眠保留原有分配权，只有显式声明才让出”，也就是有保证的唤醒：它让休眠对多模型轮流用一张卡没有意义，
也与现行代码和用户的使用方式相反。需要保证唤醒的场景以后随分时组作为可选模式再议。

**3. 节点失联重调度按运维改放置的同一套校验改写，不消耗重试次数，只在新一代跑起来之前撤回，状态在内存里；驱逐点名的副本先起后切。**
节点离线时长达到部署的重调度等待（`node_replace_after_sec`，默认 600，0 为从不）即视为失联：

- 单机副本：失联节点上的实例行移除，候选池在别的节点补位，副本没有失败，不计重试。钉在原节点上的副本无处可去，保留。
- 多机与 PD 副本：只换失联的 rank，选同计算网络（管理网兜底也可）、同厂商同架构、卡空闲、按部署配置逐 rank 试算放得下的节点，
  已有模型的优先；只有逐个换不出来、且是普通多机副本时才整组重选。结果通过 `SetDeploymentReplicaUnits` / `SetDeploymentPlacement`
  写回，经过与运维改副本列表或 PD 角色同样的校验（`planning.PlanReplicaUnits`、`ApplyPDUpdate`）；新放置的副本重新获得完整重试次数。
- 新一代跑起来之前原节点回来，放置改回；跑起来之后不再切回。这条记录只在内存里：server 重启后保留已做的替换，不撤回。
- 自动选节点要求同厂商同架构，加速器 RDMA 网络一律按有交换机处理，卡连通测试不作为约束；手动创建的混架构部署维持告警，不收紧。
- 每次重调度写 `NODE_REPLACED`，撤回写 `NODE_REPLACE_REVERTED`，无候选写 `NODE_REPLACE_NO_CANDIDATE`（最多每 10 分钟一次）。

驱逐时多机与 PD 副本也迁，采用先起后切：先在其他节点起一个替代副本（surge，每个部署一次一个），替代运行后才把放置改写过去、旧副本排空
（`NODE_DRAIN_MOVED`），没有节点可去时留在原处等待，服务副本数不低于驱逐前。这份进行中的状态同样在内存里，
server 重启后无人认领的替代副本被当作多余副本排空，迁移重新选择。强制驱逐不变：不等替代，立即撤下，不计重试。

单机扩容可在 `PUT /deployments/{id}/replicas` 里用 `place_on` 指定新副本首次放置的节点：只管第一次放置，提示保存在内存里，
此后与其他副本一样参与补位和重调度。

## 后果

- 自动化的行为都能在时间线上对应到一条运维本可手动完成的动作，出问题时排查路径就是排查那条 API；没有隐藏的优先级或策略。
- 运维必须自己安排占卡关系：两个部署共卡轮流使用时，靠定时计划成对地休眠和唤醒，或靠让位唤醒；平台不会替谁让位。
- 休眠让出容量后，唤醒可能放不回；这是明示的语义（409、等位、让位给出出路），不是缺陷。
- 没有实测时的估算只是经验值，可能偏高或偏低；实测只在实例独占卡时有，多实例共卡的休眠实例始终用估算。
- 重调度与撤回、驱逐 surge 的状态都在内存里，server 重启可能丢掉“撤回”的机会或重新选替代节点，换来不为这些短期状态新增持久化事实。
- 评估器在 server 进程内运行：server 停机期间没有任何自动动作，恢复后只补 12 小时内最新的一次计划。
- 评估器读的是“有计划 / 有闲置设置 / 有等位”的部署，不全量扫描，符合规模目标；看板按节点分页，只为当前页的节点读占用。

## 修订（2026-11-13）：重启后从事件读回撤回记录

决策 3 说节点失联重调度的撤回记录只在内存，server 重启后保留已做的替换、不撤回。实测（控制器重启用例）证实：替换后重启、原节点在新副本跑起来前回来，副本留在替换去的节点上，没有 `NODE_REPLACE_REVERTED`。改为：

- 不新增持久化。`NODE_REPLACED` 已经写明副本、rank 和两端节点的 UUID，`NODE_REPLACE_REVERTED` 写明撤回；控制器在重启后第一次看到这个部署时，从它最新的这两种事件（至多 100 条）读回撤回记录，读失败时下一轮再读。
- 只读回仍可撤回的：这个 rank 最新的一条是替换而不是撤回；放置里它仍在替换去的节点上（之后被改过的当作历史）；这个部署自替换以来没有实例在那个节点上服务过（内存里的记录在副本跑起来时就丢弃，跑过又停下的不能被切回）。最后一条按节点判断，同一部署的另一个副本在那个节点上跑过也算，拿不准时一律不读回，行为与原决定相同。
- 驱逐的 surge 进度和首次放置提示仍只在内存。

**后果。** 重启不再让一次本该撤回的替换留下来；判断不了的情形回到原来的“保留替换”。
