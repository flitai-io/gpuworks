# ADR 0088: 扩展的公开路由在整台服务端受限时按方法分类，只有声明为登录的路由照常放行

日期：2026-11-28 · 状态：已接受（收紧 [ADR 0071](0071-installable-extensions.md) 实施中「插件包不需要登录的路由在任何限制下放行」的做法；[ADR 0085](0085-external-identity-connectors.md) 决策 9 的编译模块公开路由按本页处理）

## 背景

一个模块可以用 `Host.LimitPlatform` 把整台服务端设为只读或锁定（[扩展点](../dev/extensions.md#整台-server-的可用性)）。受限时核心按路由的模式分类：读照常，改动拒绝，恢复面（登录、健康检查、控制台外壳、已接入机器的连接等）在任何限制下放行。

插件包的公开路由（不需要登录就能调用，`access: public`）原来不走这套分类，在任何限制下一律放行，理由是「提供登录的插件包得照常工作」（GWKS-477）。结果是插件包任何一条公开的写路由，在服务端只读或锁定时仍然执行。编译模块还没有公开路由；[ADR 0085](0085-external-identity-connectors.md) 第 2 步计划给它们加上 `AccessPublic`，当时打算沿用同样的豁免。「不需要登录」只说明谁能调用，不说明它是否改动东西；登录流程才是受限时必须保留的那一部分。

## 决策

1. **编译模块的公开路由：`api.AccessPublic`。** 不认证，按客户端地址限流，规则与插件包的 `public` 路由相同（默认每分钟 60 次、突发 30，超出回 429 `TOO_MANY_REQUESTS` 与 `Retry-After`）。这条链路从不读取、也从不续期会话，处理函数拿不到调用方是谁；带着有效会话 Cookie 调用，处理函数也看不到 claims，响应里也不会有 Cookie。路由照常要指明功能或标为社区路由；公开路由不能对 AI 助手可读。路由清单写 `[access=public]`。
2. **登录路由：`RouteSpec.SignIn`。** 只有 `AccessPublic` 的路由能设，否则挂载时 panic。它标明这条路由属于登录流程：身份连接器的起始路由与回调路由，包括 SAML 回传结果用的 POST。路由清单在行末写 `[sign-in]`。
3. **受限时，公开路由按方法分类。** 编译模块的公开路由与插件包的 `public` 路由，都与 `/api/v1` 下的其他路由一样：GET、HEAD、OPTIONS 是读，照常放行；其他方法是改动，只读和锁定时都拒绝。编译模块声明了 `SignIn` 的路由是恢复面，在任何限制下放行，不论方法。
4. **被拒绝的公开路由直接回平台拒绝。** 403，带限制的码（`PLATFORM_READ_ONLY`、`PLATFORM_LOCKED`，或设限模块给的说明），不先要求认证。其他 `/api/v1` 路由先鉴权再拒绝，是为了不让未登录的调用方看出有哪些路由、服务端是否受限；公开路由本来就对所有人公开，没有可隐藏的东西。
5. **插件包暂不能声明登录路由。** 它要靠清单路由上的一个新字段，而这个字段改变执行结果；按 [ADR 0071](0071-installable-extensions.md) 决策 7 须升清单 schema（今天是 1），所以与 [ADR 0085](0085-external-identity-connectors.md) 第 3 步（清单的 `sign_in`）和 [ADR 0081](0081-role-gated-plugin-routes.md) 计划的 schema 2 一起做。在那之前，插件包的公开 POST 在受限时被拒绝。

## 扩展等级

- 现状：编译模块没有公开路由；插件包的公开路由在受限时一律放行（L3 的路由，豁免是硬编码的一条规则）。
- 目标：公开路由与登录路由是路由声明（L1 接缝，`RouteSpec` 的字段与清单的访问级别），受限时由核心按同一张分类表执行。
- 准则（[ADR 0084](0084-extension-levels-and-table-kind-registry.md) 决策 3）：1 分类集中在 `classifyPlatformRoute` 与 `platformGuard` 一处；2 是否属于登录流程由扩展决定，所以由扩展声明；3 判断在逐请求路径上，只查挂载时记下的表，一次 map 查找；4、5 不适用；6 没有扩展的服务端行为不变；7 契约成本是 `RouteSpec` 的两个取值与路由清单的两个标记，只增不改。

## 取舍

- **按方法分类 vs 公开路由一律放行**：一律放行省事，但让「不需要登录」成了绕过限制的路径：一个插件包或模块的公开写路由，在服务端锁定时照样改数据。按方法分类后，受限时放行的写入只剩声明为登录的那些。
- **声明登录路由 vs 只放行公开 GET**：只放行 GET 不用新字段，但 SAML 的回调是 POST，这样就挡掉了真实的登录流程。
- **插件包现在就加清单字段 vs 推迟**：现在加要单独升一次清单 schema，而第 3 步本来要升；推迟的代价是这段时间插件包的公开 POST 回调在受限时不可用，今天没有插件包形式的身份连接器，没有实际影响。

## 后果

- 收紧了 GWKS-477（`02852bd00`）的行为：受限时插件包的公开 POST 不再放行，公开 GET 照常。这个构建还没有编进项目根密钥，没有发布过受信任的插件包。
- 身份连接器（ADR 0085）的起始路由与回调路由都标 `SignIn`。

## 实施状态

已实施：`api.AccessPublic`、`RouteSpec.SignIn`、挂载时的检查、路由清单的标记、`platformGuard` 的分类与直接拒绝，以及对应的测试与契约测试。插件包的登录路由随 ADR 0085 第 3 步实施。
