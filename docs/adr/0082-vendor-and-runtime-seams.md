# ADR 0082: 厂商与运行时各有一个接缝：厂商定义、探测流程、类型化授予、驱动注册表

日期：2026-11-24 · 状态：提议中

## 背景

平台支持的是一张「厂商 × 运行时」的矩阵。两个轴原来都靠裸字符串认身份，两轴之间的交接物是一段 Docker 命令行文本：

- **厂商身份。** `internal/accelerator` 里每个问题各有一张按厂商分支的表（名字、框架、PCI 身份、检查项、功能约束、宿主要求……）。新增厂商漏改一张，编译不报错。
- **探测。** 每个厂商的 `Probe` 各写一遍同样的流程：工具在不在、问不到时报什么、何时更新「上次看到的卡」。
- **注入。** 厂商返回 `--device`、`--runtime`、`--gpus` 这类 Docker 选项文本。docker 原样追加，nerdctl 展开设备目录，kube 翻译成 Pod 字段，udocker 重新解析并从环境变量名猜厂商。厂商要顶替 workload 自带的设置时，engine 去改 workload 的选项字符串。
- **运行时身份。** 驱动清单在选择逻辑里写了三遍；厂商的注入代码按驱动名分支，名字对不上任何一支时落到各自最后那一支。

结果是接入一个厂商要改运行时驱动内部和所有厂商共用的逻辑，接入一个运行时要读懂每个厂商的注入代码。

## 决策

1. **厂商的一切写在它自己的定义里。** `internal/accelerator/<厂商>.go` 里一个 `vendorSpec` 值：身份（名字、别名、框架）、怎么在主机上认出它的卡（工具、控制设备、PCI 身份与型号名、架构推导）、能在什么上面跑负载（运行时、宿主要求、功能、dGPU 后端、运行时插件）、怎么检查它的卡。`accelerator` 包里回答厂商问题的函数都查这份定义，签名不变。
2. **没声明就是不支持。** `supports` 没列的功能、`runtimes` 没列的运行时，server 在调度前拒绝，agent 在准入时拒绝。`runtimes` 是「这家的卡能不能承载负载」的唯一陈述：一个都不列，就是只发现和监控。
3. **探测流程归框架。** `gpu.probeCards` 持有读工具的厂商共有的流程；厂商只回答工具装了没有、工具的输出怎么变成卡。身份基线统一为 `cardBaseline`，只有问到了答案才替换。AMD（读 sysfs，出错时仍返回已读到的卡）与 Apple（不在 PCI 总线上）不走它。
4. **授予带类型，不带容器命令行。** 厂商返回 `runtime.DeviceGrant`：设备节点、runtime class、对 NVIDIA Container Toolkit 的设备请求、附加组，以及它顶替 workload 自带的哪些设置（`Replaces`）。每个运行时驱动自己渲染。workload 自带的选项不被改写，读的时候由 `WorkloadSpec.OwnDockerArgs` 略去被顶替的部分。
5. **运行时驱动有注册表。** `runtime.Drivers()` 一处列出每个驱动的名字、不能运行的系统、是否自己保存镜像，以及它的容器看到哪些设备（`DeviceView`：只看到被授予的、看到宿主机的、没有容器）。厂商收到的是 `runtime.Target`（名字加视图），按视图决定怎么授予。视图未知的运行时在 `gpu.ResolveInjection` 统一拒绝；没有容器的运行时收到非空授予也在那里拒绝。
6. **注册是编译期的显式列表。** 厂商定义在 `vendorSpecs` 里列一行，驱动在 `defaultProbers` 里列一行。不用 `init()`，不做运行时安装的厂商插件。
7. **用测试和预算守住。** `TestVendorDefinitionsAreConsistent` 检查任何一份定义都必须成立的规则，不点名任何厂商；`TestVendorRuntimesAreTheAgentsDrivers` 保证厂商能列的运行时与 agent 的驱动是同一组名字。`scripts/arch-constraints.txt` 有四条只降不升的预算：注入路径上按驱动名的比较、手写的容器选项字面量、定义与驱动之外按名字判断厂商的文件数、udocker 里从环境变量名推断厂商的函数数。

## 取舍

- **两处登记，不是一处。** 定义在 `accelerator`（server 与 agent 共用），驱动在 `agent/gpu`（依赖 `accelerator`）。合成一行登记需要 `accelerator` 反过来依赖 `agent/gpu`，agent 的代码就会进 server 的二进制。
- **运行时安装的厂商插件（未采纳）。** 厂商驱动跑在每个节点的 agent 上，探测与设备授予就在启动路径里；做成插件要给 agent 再造宿主、签名分发与版本协商。接缝收好之后，将来要让厂商自己交付二进制，可以把同一层接口搬到进程外。
- **`init()` 自注册（未采纳）。** 少写一行登记，代价是「平台支持哪些厂商」不再能在一个文件里读到，登记顺序取决于文件名。
- **`runtimes` 对每个厂商都严格。** 测试替身用的驱动名也不例外，所以测试环境的假驱动以它所代替的运行时的名字出现。
- **没有上报运行时的节点。** 只有要求特定宿主（操作系统或架构）的厂商因此拒绝，其他厂商等节点上报后再判断。这是原有行为，保留。
- **没有厂商名的 workload 仍按旧办法判断。** udocker 把 workload 记在磁盘上，旧 agent 写下的记录没有类型化的授予，所以它从环境变量名推断厂商、解析 `--device` 的逻辑保留为回退路径。新厂商不需要在里面加条目。
- **降级。** 新 agent 写下的 udocker 记录把授予的设备放在类型化字段里。旧 agent 读得出这份记录，但不认识其中的授予：降级后对已在运行的 udocker 容器打开终端或执行命令，能打开，但里面没有绑定授予的设备；记录里没有设备选项可供推断时，它按环境变量名来准备（PPU 的 workload 因此被当成 NVIDIA 的）。容器本身不受影响，重新部署后恢复。

## 仍在定义之外的

- `InferVendor` 从型号名、架构名里找产品线标记的规则（`accelerator/infer.go`），以及 Kubernetes 扩展资源名到厂商的映射（`accelerator/kube.go`）。两者都是一个函数里按固定顺序试的规则，顺序本身是行为。
- engine 里按驱动名的判断：dGPU 注入器（`agent/engine/partition_hygon.go`、`partition_ascend.go`）、`engine.go` 里 kube 的宿主机根目录、`runtime_mounts.go` 里 docker 的挂载根目录；以及海光 dGPU 后端手写的 `--tmpfs`。预算记着它们的数量。
- 控制台的图标与译名仍写在前端；厂商的顺序、名称与框架归属由 server 的厂商字典下发。
- 支持矩阵（`docs/reference/support-matrix.md`）里声明的支持范围由定义生成；按「厂商 × 运行时」的验证程度仍是手写的。

## 后果

- 接入一个厂商：一份定义、一个驱动、各登记一行，加真机夹具。不改任何运行时驱动。步骤与评审规范见 [接入一个新的加速卡厂商](../dev/add-accelerator-vendor.md)。
- 接入一个运行时：一个驱动、注册表里一项，写明它的容器看到哪些设备，加上 `accelerator` 里它的名字常量。厂商的驱动不用改。但 `runtimes` 是严格的：一个厂商在自己的定义里列出它之前，它的卡在这个运行时上被拒绝，而列出来要有真机证据（评审规范第 8 条）。新运行时因此是逐个厂商开放的。
- 「这个组合支不支持」在调度之前就有答案。
