# ADR 0068: 带显存上限的分区按剩余显存与平台外进程共用一张卡

日期：2026-11-16 · 状态：已接受，2026-11-17 修订（补充 [ADR 0060](0060-card-health-from-hardware-facts.md)）

## 背景

卡上有不是平台启动的计算进程（用户自己起的 vLLM、另一个编排器的容器）时，agent 把它们报为 `foreign_processes`，server 把这张卡当作不接受任何部署：卡的显存被平台看不见、也规划不了的东西占着，整卡部署会在启动时显存不足。

但带显存上限的 dGPU 分区（nvidia-dgpu 等）本来就只要卡的一部分，agent 也报了这些进程各占多少显存。实际案例：一张 143771 MiB 的 H20-3e 上另一个编排器的容器占 63982 MiB，一个 50 GiB 的分区部署被一律拒绝；手工清掉 `foreign_processes` 后它和那个容器在同一张卡上稳定并行。

只在 server 端放开不够：agent 判断平台外进程的规则是「卡上没有本节点实例时，卡上的进程都是外部的」，卡上一旦有了平台实例就不再检查这张卡，原来的外部进程从下一次上报里消失，server 会以为卡空了，把剩下的显存当成全部再分出去。

## 决策

1. **只给分区共用，按显存放行。** 卡被平台外进程占用、这些进程的显存都已知、卡本身健康且没被管理员停止调度时，带显存上限的部署可以放到这张卡上：可用显存 = 总显存 − 外部进程占用 − 余量 − 平台已有实例的占用（休眠残留照算），够这个部署的上限加分区开销（`estimate.PartitionClaimBytes`）才放行。整卡部署照旧拒绝，`store.GPU.CanTakeWork` 的含义不变，fleet 统计与 SQL 聚合都不受影响；调度中心的卡片状态里，有平台实例在上面提供服务的被占用卡算「提供服务」，其余照旧算「被平台外进程占用」。同一口径也用在运行中分区原地改配额（`planning.QuotaRoom`）和 GPU 列表的可用显存上（`planning.ForeignHold`）；外部占用未知的被占用卡上，原地改配额只能缩不能涨，GPU 列表的可用显存为 0，不把未知当成没人占用。用量分析的 GPU 时间只把调度器确实能放分区的被占用卡（共用条件成立、agent 达到第 5 条的等级、卡上有就绪的分区后端，`planning.PartitionMayShareHeldCard`）计为可调度容量，因为分区的时长就记在它上面。管理员临时放开调度的被占用卡，整卡部署照旧按整卡容量（总显存 × 利用率）放行、不扣外部占用，`no_fit` 也只在扣过外部占用的容量上带外部占用参数。
2. **余量**：`estimate.ForeignHeadroomBytes` = 卡的 5%，至少 4 GiB，与 L1 休眠的主机内存余量同形。外部进程的显存是每分钟一次的读数，不是它们守的上限，一旦显存不足，挤掉的是双方。
3. **未知就不共用**：某个进程没有显存读数、占用者不是进程（Kubernetes 分给别的 Pod 的卡，没有 PID）或清单读不出来，都按「占用未知」处理，卡保持拒绝。
4. **agent 在共用卡上按进程数认定外部进程**：卡上有了平台实例后，agent 不再完整检查这张卡；但如果这张卡与此前认定的外部进程共用，agent 每轮照样读它：平台的每个引擎在一张卡上只留一个进程（休眠残留的读数依赖同一条规则），卡上的平台实例有几个，就有几个进程算平台自己的。此前认定为外部、按 PID 加进程名还在清单里的进程仍是外部的，报它当前的显存（工具这轮没给读数时报它最后一次的显存）；已经认作平台引擎的进程仍是平台的；其余新出现的进程先补齐平台引擎还没认到进程的名额，超出的都是外部的——外部用户在旁边新起的作业，或对方编排器换 PID 重启的负载。同时新出现的进程比空名额多时，占显存最多的算外部：高估外部占用只会拒绝一次放置，低估会让分区显存不足。清单里已经找不到的外部进程不再上报，但它的显存不会立刻放出来：卡上没有外部进程剩下时，照旧连读 3 次空闲才解除，所以退出、换 PID 重启的间隙和开机前留下的无 PID 记录都不会在平台实例在卡上期间一直挂着。共用过的卡在平台实例留在卡上期间一直这样读，外部负载解除后再回来也能重新发现。卡上的平台实例全部休眠或全部离开时，这张卡重新被完整检查。探测失败或进程清单读不到时重述上一次的结论，不清空。外部进程记录存在 agent 状态目录（`card-occupancy.json`），agent 重启或升级后接着用（认作平台引擎的进程只在内存里，重启后按名额重新认）；文件最后写入早于本次开机（`/proc/stat` 的 `btime`，读不到时同样处理）时，PID 已没有意义，读入时去掉记录里的 PID：这些进程不再拿去对活进程，免得把恰好拿到同一 PID 的平台实例进程当成外部进程，卡在下一轮按上面的规则重新读。判断只用文件已有的修改时间，文件格式不变。它只在 agent 本地，不是 server 新增的持久化事实。
5. **按 agent 能力把关**：共用只对做到第 4 条的 agent 开放，判断复用节点已上报、每次上报都刷新的 `partition_safety_protocol` 等级：`proto.PartitionSafetyForeignTracked`（2）表示 agent 在分区与外部进程同卡时继续上报外部进程。这是同一份「分区安全约定」的下一级（1 级是原生 vdev 的属主约定），高等级包含低等级，回滚 agent 会在下一次上报时撤销新的共用。已经放在被占用卡上的分区不受这个撤销保护：旧 agent 不再上报卡上的外部进程，server 会把这张卡当成空闲卡，按全部显存再放部署。把 agent 回滚到 2 级以下之前，先停掉放在被占用卡上的分区。不新增列。
6. **休眠**：唤醒到被平台外进程占用的卡上照旧拒绝；为了一致，会休眠的部署也不放到这样的卡上，拒绝码 `held_outside_platform_sleep`，否则它睡下后在这张卡上永远唤不醒。
7. **说清楚**：指定了卡的请求，过滤阶段只看指定的卡，被占用的卡报 `gpus_held_outside_platform` 而不是「没有空闲 GPU」；显存不够时 `no_fit` 带上 `foreign_bytes`/`foreign_gib` 与余量参数，界面据此说明数字。部署表单里这张卡是否可选由 server 对当前请求的逐卡结论（`gpu_candidates`）决定，前端不重写规则。

2026-11-17 修订（第 8–12 条）：分区只隔离显存，算力与带宽仍与平台看不见的负载共享，用户会看到原因不明的推理变慢。所以共卡改为需要同意，且总是先用干净卡。

8. **节点放置策略开关，默认关**：节点的放置策略（`nodepolicy.Policy`，节点行的 `placement_*` 列，按 `nodepolicy.Settings` 驱动字典 `GET /scheduling/node-placement-policies`、`PATCH /nodes/{uuid}/placement-policy` 和 DTO）有一个旋钮 `share_with_foreign`，默认关。关闭时自动放置不使用被占用卡，即回到本 ADR 之前的行为；拒绝码 `held_outside_platform_not_allowed` 带 `setting`（旋钮的键）、`gpus`、`count`、`node`，界面按 `setting` 显示旋钮自己的名字。节点上另有干净卡但忙或放不下时也报这个码：调度失败、且有卡被可同意的闸扣下时，调度器在内存里按「已同意」再试一次，能放下就报这个码，放不下就报那时剩下的原因（打开开关也帮不上）。用量分析只在开关打开的节点上把被占用卡计为可调度容量（`planning.PartitionMayShareHeldCard`）；外部占用的显存口径与开关无关。这是运维的意愿，无法从现有数据推出，所以新增一列（迁移 218）。旋钮写入不按适用性拒绝：节点没有就绪的分区后端或 agent 低于第 5 条的等级时，`placement_policy_availability` 标为不生效并给出原因码。
9. **卡准入闸与卡偏好档**：共卡是调度器的一道可同意的卡准入闸（`scheduler.cardGate`），不改卡的能力位：`ForeignShareable` 仍只表示「能共用」，闸决定「是否允许共用」，闸表的顺序就是拒绝原因的优先级（休眠闸在前，同意也不放行）。「优先干净卡」是卡偏好档（`scheduler.cardPreferences`）的第一项：表序就是优先级，档位按表序的字典序放宽，先放宽告警卡、最后放宽外部共卡，即「健康且干净 → 告警但干净 → 健康但共卡 → 都可」。方案用到共卡时带 `foreign_shared_gpus_used{gpus,count,foreign_gib}`。更干净的档优先于目录偏好更高的共卡方案。跨节点时，只有共卡这类让步（`poolWide`）才让控制器的池放置和部署表单的自动放置预览（共用 `planning.FitPicker`）在试算预算内继续找有干净卡的节点；找不到就用共卡的后备，且后备优先于等待别人让出；告警卡仍按首适配。操作者点名节点启动的副本（`lifecycle.Orders.HintPlacement`）只要在该节点放得下就放在那里：偏好只给调度器自己挑的节点排序，不推翻操作者点名的节点。
10. **手工选卡即同意**：同意只来自部署放置里的 `gpus` 键（`planning.Placement.OperatorPinned`，非自动放置），PD 单元和多机 rank 上的 `gpus`（`units[].gpus`、`followers[].gpus`，由 `planning.PDRankLaunch.Apply` 带进该 rank 的放置）同样算：平台自己挑的单元和节点替换只写节点、不写卡。开关关闭时，手工钉到被占用卡且显存放得下的请求照样放行。任何 API 调用方（包括 AI 助手的通用 API 工具和脚本）用 `gpus` 钉卡都算同意；旧客户端回显方案用的 `gpu_indexes` 不算，平台自己填的卡号（逐卡能力探测、单元建议、池放置到别处的副本）也不算。部署表单的选卡列表按「操作者在选」判断，共卡标 `foreign_shared_card` 提示。整卡请求和外部占用未知的卡照旧拒绝。
11. **关闭开关不驱逐**：只影响新的放置。重新放置（滚动重启、故障替换、扩容）按新值判断：滚动重启在排空放在被占用卡上的分区之前，先在该节点上不计这个实例地试算替换（`planning.Input.ExcludeInstanceUUID`），被开关拒绝就停住并记录 `held_outside_platform_not_allowed`，不拿掉副本；崩溃后的故障替换无法预检，会因开关关闭进入待放置，原因码指明开关。节点要求没把副本钉在一个节点上的池部署不预检：它的替换由池放置在整个池里挑节点（`pickPoolNode`），原节点的拒绝说明不了替换会落在哪；整个池都放不下时，替换进入待放置，原因码指明开关。
12. **实例共卡提示**：实例所在的卡与平台外进程共用时，实例带一条提示（`dto.Instance.notes`，`INSTANCE_CARD_SHARED_OUTSIDE{gpu_indexes,foreign_bytes,foreign_gib}`，外部占用未知时为 `INSTANCE_CARD_SHARED_OUTSIDE_UNKNOWN`）。只有仍在卡上的实例带提示：已结束的（`proto.InstanceFinishedStates`：stopped、failed、pending_removal）不带，排空中和删除中的照带。提示在读实例时由规则表推导（`deployment.InstanceNotes`），不持久化、不按实例保存状态：外部进程上报后下一次读就出现，解除后消失，实例删除后什么也不留。它陈述事实，不看协议等级和放置方式。「之后才出现」的外部进程靠 agent：`proto.PartitionSafetyForeignTrackedPartitioned`（3）的 agent 把只放着分区实例的卡也按第 4 条的名额规则读（每个分区引擎在卡上一个进程），所以后起的外部进程也会上报。第一次读这张卡时（刚从低等级升级，或重启期间有作业在旁边启动）进程比我方引擎的名额多、又都不认识，哪些是我方的只能猜：占显存多的算外部（宁可多报），但这个猜测不当作已知——下次读照样重新判断、写进状态文件时不带 PID，外部作业走后被错认的我方引擎重新算我方，提示随释放轮次消失。**不覆盖**：放着整卡实例的卡上后起的外部进程（整卡引擎的进程数不固定，按名额认定会误判），以及等级低于 3 的 agent。

## 取舍

- agent 仍不按 cgroup 把进程对到容器：那需要各运行时、各厂商工具的 PID 命名空间处理，误判会把平台自己正在用的卡停掉。共用卡上改按「每个引擎每张卡一个进程」的名额认定：平台实例已经在卡上、但引擎进程还没起来时出现的外部进程会占掉这个名额，被当成平台的；一个引擎在卡上多开进程时，多出的进程会被当成外部的，少放行。只在与外部进程共用过的卡上这样读，其余平台实例的卡仍不检查。
- PID 加进程名可能在 PID 复用时把同名的新进程当成原来的外部进程，上报的是那个新进程的显存；同一次开机里这种情况少见，开机之间不再按 PID 匹配。
- 外部进程退出后，卡在 3 次读数内仍按它最后一次的显存计；之后才放出来。重启超过这段时间的负载在这期间按空闲计，回来后作为新进程重新算外部的。
- 余量用固定比例而不是外部进程的历史峰值：峰值需要新的持久化事实，而 5%/4 GiB 已覆盖实测的读数波动；管理员仍可以停止这张卡的调度。
- 旧 agent 的节点在升级前不能共用：宁可让用户升级 agent，也不在第一次放置后把卡误判为空闲。
- 本 ADR 取代 `known-issues.md` 里原来的搁置项 T68（「外部进程占用的卡只做整卡排除」）。
- 同意不折进能力位 `ForeignShareable`：折进去后下游分不清「不能共用」和「不允许共用」，手工选卡也没有可以覆盖的对象，拒绝原因也说不出该去开哪个开关。
- 「优先干净卡」用偏好档而不是罚分：`scorePlans` 只在不同 TP 的方案之间比较，同一 TP 的卡组已由拓扑选定，罚分改变不了选哪张卡。
- 告警卡不跨节点继续找：那会改变今天所有带告警卡节点的首适配行为，而告警卡是平台看得见、在监控的卡。
- 放置策略的 PATCH 不按适用性拒绝：适用性随分区后端是否就绪、agent 版本变化，拒绝写入会让运维在后端短暂未就绪或 agent 回滚时关不掉开关，也不能在升级前先设好。
- 同意重试只在调度失败时多跑一次纯内存的方案；偏好档最多 2^n 次（表项上限 4），只有前一档为空才往下走。
