# ADR 0035: server 持有一对平台 SSH 密钥，带外恢复优先用它

日期：2026-10-03。状态：已接受。修订 [ADR 0006](0006-out-of-band-recovery-ssh-credentials.md) 中“保存认证材料”的部分。

server 首次启动时生成一对 ed25519 密钥（平台密钥），私钥用 `auth.Secretbox` 加密存入 `platform_ssh_keys` 单行表，公钥与指纹明文存。SSH 纳管、预检查、带外恢复和云厂商一键安装都先用平台密钥登录：

- 运维只需在目标机授权一次平台公钥；界面给出一行授权命令。
- 用户改用密码或自己的私钥登录时，登录成功后 server 把平台公钥追加进该用户的 `authorized_keys`（按密钥本体去重），此后节点 SSH 凭据只记端点，**不再保存密码或私钥**；写入失败才退回保存用户给的凭据。
- 节点 SSH 凭据不加“认证方式”字段：secrets 为空即平台密钥，这一含义由删除旧的“读 server 的 `~/.ssh`”回退保证唯一。
- 云厂商：RunPod 把公钥追加到账号 SSH Key（Pod 启动时注入）；Vast 经接口挂到实例；CompShare、AutoDL 只给密码，用接口返回的实例密码登录一次后写入公钥。

所有 SSH 登录都经 `provision.DialSSH` 一处构建认证顺序（平台密钥 → 用户私钥 → 用户密码 → 实例密码，显式指定方式时只试那一种），安装报告固定给出“SSH 认证”（试了什么、哪个被接受）与“平台公钥”（已在 / 本次写入 / 写入失败及原因）两行，排查时不需要猜 server 用了哪份凭据。

**当前认证协议补充（GWKS-205）**：请求新增 `auth_mode: "keyboard_interactive"`，复用 `password` 字段，只处理一次非回显密码应答（允许有限的无问题信息轮次），不支持多问题、多次口令或 MFA。显式模式仍只试选择的方式；自动模式保持上面的原有顺序，再用请求或已保存的 `password` 尝试键盘交互认证。落库规则不变，不新增认证协议字段：保留口令的凭据读取仍返回 `auth_mode: "password"`，该值只表示凭据类型；恢复在自动模式下兼容两种密码协议。安装/保存时仍优先授权平台公钥，成功清除用户秘密，失败才保留。

## 权衡与后果

- 安全边界与 ADR 0006 相同：能读库与 `data/master.key` 的人能拿到平台私钥并登录所有授权了它的节点；但库里不再长期存放各节点的密码，用户改密码也不影响恢复。
- 一把密钥对应全部节点：泄露时需要在设置页重新生成，并在各节点重新授权；重新生成不会自动替换节点上的旧公钥（需要逐台登录，代价与风险都不小），界面在确认框里写明影响。
- RunPod 账号 key 只在 Pod 启动时注入，已在运行的 Pod 第一次仍需用户提供私钥；之后同样只靠平台密钥。
- 写入 `authorized_keys` 是对目标机的修改；只发生在安装与保存凭据时，预检查保持只读，只报告“安装时写入”。

## 未采用方案

- 读 server 运行用户的 `~/.ssh`：默认部署以 `gpuworks` 系统用户运行，`HOME` 为安装目录，没有 `.ssh`；unit 不写 `User=` 时 `HOME` 为空。读到的往往不是管理员以为的那把钥匙，且没有界面能看到它是哪把。
- 每个节点生成独立密钥：授权与轮换都要逐台进行，换来的隔离在 server 被攻破时并不成立（所有私钥都在同一个库里）。
- 继续保存密码：密码会过期或被改，且库泄露即得到可复用的口令。
