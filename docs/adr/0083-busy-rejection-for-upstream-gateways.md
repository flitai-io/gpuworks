# ADR 0083: 繁忙婉拒：放在前面的网关声明「忙就别排队」，由 GPUWorks 在准入时判断

日期：2026-11-26 · 状态：已接受

## 背景

有的站点在 GPUWorks 前面再放一个网关，同一个模型名后面除了 GPUWorks 还有别的上游（例如公有云）。这个网关希望本地算力吃紧时把请求转去别处，本地腾出位置后马上回来。

业内 AI 网关的改投都是「失败后改投」：等到 429、5xx 或超时才换上游。GPUWorks 原来从不因为忙而拒绝请求，副本占满时请求在引擎里排队，前面的网关只能等它超时，或者自己估计 GPUWorks 忙不忙。

前面的网关还需要知道它用的 API 令牌在 GPUWorks 里能用哪些优先级类、哪些模型按优先级调度，才能决定该怎么带 `X-GPUWorks-Priority-Class`。这些原来只在管理面看得到。

## 决策

1. **调用方声明，GPUWorks 在准入时判断。** 模型请求带 `X-GPUWorks-If-Busy: reject` 表示「忙就别排队」。GPUWorks 判断当前接不了这个请求时立即返回 429 `MODEL_BUSY`，带 `Retry-After: 1`；判断接得了就照常转发。只有取值 `reject` 算声明，其他取值与不带相同；这个头不转给引擎。不带声明的请求行为与以前完全一致。值不值得为了不排队而去别的上游，仍由前面的网关决定，因为只有它知道后面还有没有候选。
2. **对外的契约是语义，口径是内部实现。** 调用方只按状态码与 `error.code` 识别婉拒，不匹配 `message`，也不依赖「接不了」是怎么算的。口径以后可以变准（例如把下面不婉拒的情况纳入、或跨 server 汇总），语义和接口不变。
3. **第一版的口径：所有可选副本都没有空闲运行位。** 副本的运行位是实例启动参数里明确写出的并发序列上限（vLLM `--max-num-seqs`、SGLang `--max-running-requests`，参数字典的 `max_num_seqs`），由 `deploy.RunSlots` 读出。副本上本请求要排在其后的在途请求数达到运行位，就算没有空位：按优先级调度的副本（实例带着优先级调度启动、网关向它写引擎的 `priority`）只计优先级数值不低于本请求的，更低的不计；其他副本按到达顺序运行，所有在途请求都计。部署的路由策略首选的副本满了而别的可选副本有空位时，请求落到有空位的副本。
4. **判断与占位是同一步。** 判断放在副本选择器的锁里、取租约之前（`balancer.hasRoom`），两个并发请求不会都拿到最后一个空位。在途数按优先级分别计数（`inflightCounts`），租约释放时按占位时的类退还。
5. **拿不准就不婉拒。** 以下情况照常转发或按原有规则处理：有运行中的副本运行位未知（启动参数没写明上限、值不是正整数、shell 还要展开的值、数据并行规模不为 1）的部署，按部署整体判断，与当时可选的副本是哪些无关，和 `/v1/key` 的 `busy_reject: false` 一致；PD 分离部署、多机部署、休眠或唤醒中的部署、连接失败后换副本的重发、被抢占后的重放、`/v1/tokenize` 等辅助接口与试验场（声明被丢弃）。
6. **婉拒不是这个部署的请求。** 它计入部署网关请求数的 429 一类，不留请求记录，不更新部署的最近请求时间。错误的 `type` 是 `invalid_request_error`：网关的错误表规定只有 5xx 用 `server_error`。
7. **令牌信息接口。** `GET /v1/key` 用 API 令牌鉴权（同 `/v1/models`），返回：本 server 支持的网关能力 `features`（`priority_scheduling_header`、`busy_reject`，只增不减）；令牌的优先级绑定 `priority`（`own`、`ceiling`、`reachable`，匿名访问为 `null`），由 `priority.KeyReach` 按 `Resolve` 的同一套规则算出，调用方只用「在 `reachable` 里就按它，否则按 `ceiling`」一条规则；令牌有权调用的每个模型的 `priority_scheduling`（`all`/`some`/`none`）与 `busy_reject`（会不会被婉拒）。它从路由表与优先级类快照回答，不读部署表，不是推理流量。响应头 `X-GPUWorks-Priority-Scheduling: on|off` 说明这一次引擎是否按类调度。
8. **多个 server 时各数各的。** 第一版的在途数是每个 server 进程内的租约计数，不跨 server 汇总。结果是少算：该婉拒时可能没婉拒，不会误拒。

## 取舍

- **让前面的网关轮询负载、按排队深度改投（未采纳）。** 引擎的排队数随指标采集周期更新，到网关时已滞后数秒以上；按滞后的数做比例改投会振荡。排队数与容量脱钩：并发序列上限大的部署过载时排队数仍可能是 0。逐请求抽签还会把进行中的会话一轮轮赶到别的上游。GPUWorks 手上的在途数是实时的，在准入那一刻判断没有控制环，也就没有振荡。
- **在每个响应头里带负载（未采纳）。** 流量一旦改投走，网关就看不到本地何时恢复；饱和时首字节最慢，头恰好在最需要的时候最不新鲜。
- **在按优先级调度的副本上按总在途数判断（未采纳）。** 这样的引擎会让高优先级的请求先运行，优先级更低的排队请求不构成本请求的等待。按总数判断时，低优先级的批处理占满队列，普通请求会被白白赶走。没有按优先级调度的副本按到达顺序运行，在那里总数就是本请求的等待，所以按总数判断。
- **高优先级请求不婉拒（未采纳）。** 按第 3 条的口径，高优先级请求只在运行位被同级或更高的请求占满时才被婉拒，那时留在本地也只是排在同级后面。数据能不能离开本地由前面的网关的规则表达，不由优先级表达。
- **运行位未知时按引擎默认值算（未采纳）。** GPUWorks 不知道每个引擎构建的默认值，猜错的代价是误拒。没有写明上限的部署在 `/v1/key` 里 `busy_reject` 为 `false`，前面的网关据此知道对它声明无效；以后找到可靠的判断办法，只是该模型的 `busy_reject` 变为 `true`。
- **PD 分离与多机部署不婉拒。** 它们的运行位不是单个副本的租约能数清的；按一段或一个 rank 判断会误拒。
- **第一版不跨 server 汇总。** 汇总需要 server 之间的实时通道或引擎上报的排队数，后者有采集滞后。少算只会让请求照常排队，与没有这个功能时相同。
- **不在请求记录里留婉拒。** 婉拒发生在毫秒内、没有到达引擎；前面的网关自己的调用记录里有这一次尝试，GPUWorks 的 429 计数足以看出婉拒的量。
- **旧版本 server 没有 `/v1/key`。** 它把这个路径当作没写模型的模型请求，带有效令牌时返回 400 `MODEL_REQUIRED`，不是 404。前面的网关把 401、403 之外的非 200 都当作「不提供」即可。旧版本不认 `X-GPUWorks-If-Busy`，照常转发，行为与以前相同。

## 后果

- 前面的网关可以在本地没有空位时立即改投，本地一有空位新请求就回来，无需轮询。
- 要参与繁忙婉拒，部署的启动参数里必须写明并发序列上限；接入步骤见[请求优先级](../explanation/request-priority.md#上游网关接入)，接口见 [OpenAI 兼容网关](../reference/openai-gateway.md#繁忙婉拒)。
- 副本选择的结果不变：优先级只用于判断有没有空位，不影响选哪个副本；不带声明的请求走与以前相同的路径。
- 口径调整（跨 server 汇总、纳入运行位未知的部署）不改接口，只改 `models[].busy_reject` 的取值与婉拒的时机。
