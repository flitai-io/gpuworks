# Image Catalog and Inference Image Families

GPUWorks assembles the complete engine command itself and does not depend on the image's default entrypoint. The Images page manages runtime images by series → version → node distribution,
with versions divided into three source categories. These are source labels on the same type of image version record, not three different object types:

| Source (UI) | `source` in the Database and API | Maintained By | What Can Be Changed |
|---|---|---|---|
| System | `official` | The image catalog manifest published by GPUWorks | Metadata is read-only and cannot be deleted; operators can enable or disable series and versions and add acquisition addresses (such as archive URLs) to versions. Only manifest updates can delete or deprecate them |
| Community | `community` | You select and add tags from community repositories | Editable; deletion is available in the details drawer |
| Custom | `custom` | You enter arbitrary references to add images | Same as above |

## Node Image Identity and Periodic Inventory

In image series details, `GET /api/v1/images/{id}`, a version's node row exposes `image_digest_id` as the **runtime image ID** most recently reported by that node.
Docker reads `Id` and runtime size from the same `docker image inspect` result. This `Id` is the image config digest,
not a registry manifest/index digest or the catalog's integer ID. It is also available after an offline `docker load`;
do not use it as a registry digest to construct pull references, verify manifests, or infer archive bytes.

The Agent's periodic `status.node` message reports these fields in `images[]` (image portion only):

```json
{"images":[{"image_ref":"registry.example/team/runner:v1","present":true,"image_id":"sha256:1111111111111111111111111111111111111111111111111111111111111111","runtime_size_bytes":8192}]}
```

`image_id` is an optional string; an empty value is omitted during encoding. A runtime that did not observe an identity, or an older Agent, may report presence alone.
The server trims whitespace around the ID; an empty result also means unobserved.
`runtime_size_bytes` is a separate runtime measurement; omission means unknown. Legacy `size_bytes` and transfer-progress bytes do not establish that measurement.
A failed runtime inspection omits that report entry. Neither an inspection failure nor a missing report establishes image absence.

The server reconciles only catalog-known `image_ref` values, with these identity-update rules:

| Inventory result and current state | Treatment of `image_digest_id` |
|---|---|
| Present, with a nonempty `image_id`, and no active pull or sync | Adopt the trimmed runtime ID; update it when the same reference resolves to a different ID |
| Present, but `image_id` is omitted or empty | Keep an existing ID; a newly created node row remains unknown, preserving older-Agent compatibility |
| A presence report arrives during a pull or sync | Do not adopt its new ID; retain the transfer state, with completion and failure still decided by explicit transfer results |
| Explicit `present: false` | Clear the old ID, including on pulling, syncing or failed rows; retain an active transfer state or an already-recorded failure |

A presence inventory therefore cannot mark an active transfer complete; clearing identity on explicit absence does not itself mark that transfer failed.
`present: true` only establishes presence of that reference. Without a new ID, the retained value may come from an earlier observation and does not establish that this inventory verified the identity again.
A settled node row is not rewritten when its state, identity and sizes are unchanged.

### Startup Sync

The embedded seed is the image catalog shipped with the server binary. The server decides whether to sync this catalog into the database
based on whether the build has changed ([ADR 0040](../adr/0040-signed-multi-source-distribution.md)):

- On the first startup after a build change (a binary upgrade or reinstall), including when you run `gpuworks migrate`, the embedded seed is synced after the database opens and before any component resolves images. This requires no network access and prints the sync log below.
- Subsequent startups of the same build do not replay the seed. The database retains the last imported catalog, whether it came from checking for updates, uploading a manifest, or the previous seed replay. The log reads `official catalogs kept from their last import`.

```text
image catalog synced catalog_version=2026-10-09.f085e40b created=0 updated=25 deleted=0 deprecated=0 skipped=0
```

The sync rules are the same as for manual catalog updates (see the next section), except for conflict handling: if a seed entry conflicts with a community/custom row through a same-named series or identical ref,
startup sync logs an `image catalog entry skipped` warning and skips that entry without blocking startup.

### Updating the Catalog

There are only two update paths for the system catalog, both on the Images page's System tab:

- **Check for updates**: `POST /api/v1/images/sync`. The server reads the signed index for the current channel from the release channel, downloads the image catalog listed in it, and verifies it against the
  sha256 in the index (see the [configuration reference](configuration.md#镜像目录与镜像拉取)). If no release source returns a usable index, it returns 502
  `UPDATE_SOURCES_UNAVAILABLE`. If the index is usable but no source provides a catalog file matching it, it returns 502 `UPDATE_DOWNLOAD_FAILED`
  (both include each source's reason in `detail`). If the channel has not published an image catalog, it returns 404 `UPDATE_NOT_PUBLISHED`. The database remains unchanged in all these cases.
- **Upload manifest**: `POST /api/v1/images/import`, with the manifest JSON itself as the request body. Use this when the server cannot access the internet:
  on a machine with internet access, download the current channel's `<channel>/manifest.json` from any release source (such as `https://dl.gpuworks.ai/release/manifest.json`, the same file as the image catalog in the channel's index), then upload it.

Both paths record the imported `catalog_version` as the current catalog version. The settings page's Version and updates section uses it to show whether updates are available.

Both paths share the following import rules with startup sync:

1. Add or update (upsert) series and versions by `image_ref`. Preserve the enable/disable settings operators configured for series and versions, as well as user-registered archive URLs
   (acquisition addresses starting with `http(s)://`) on system versions.
2. For system versions no longer in the manifest (usually because the same tier got a new revision, for example r1 replaced by r2): delete those that have no references and are on no node directly
   (along with their distribution records on all nodes, and delete the series if it becomes empty). Keep those that still have references, or that some node has already pulled (distribution state `present`), as an **older version**:
   the API field `deprecated` is `true`, `deprecated_since` is set to the current `catalog_version`, and the Images page shows “Older version”, or “Older version · N references” when it has references.
   An older version keeps working, and new deployments no longer pick it; once it is removed from every node, the next catalog sync removes the row.
   A “reference” means a match in any of `deployments.image`, unfinished `instances.image` (excluding `stopped`, `failed`, and `pending_removal`),
   or `models.image_id`. The same definition applies when deleting community/custom images: deletion of a version or series that is still referenced is rejected (409 `IMAGE_IN_USE`);
   being present on a node is not a reference and does not block deletion.
3. During a manual update, if a manifest entry conflicts with a community/custom row through a same-named series or identical ref, the entire import returns 400 `IMAGE_IMPORT_CONFLICT`
   and writes nothing.
4. Importing the same manifest twice produces the same result. There is no version comparison, downgrade prevention, signature verification, or source verification: the imported content is used as provided.

Response (the startup sync log uses these same counters):

```json
{"catalog_version":"2026-10-09.f085e40b","created":0,"updated":25,"deleted":0,"deprecated":0,"skipped":[],"series":[...]}
```

### Manifest Format

The embedded seed and upstream `manifest.json` are the same file. `schema_version` must be `3` (`2` is also accepted for compatibility; other values return 400
`IMAGE_MANIFEST_INVALID`). `catalog_version` is required, takes the form `<date>.<first-8-content-hash-characters>`, and is used only for display and logging,
not comparisons. The optional `sha256` is a content integrity hash (calculated over canonical JSON with the `sha256` field set to an empty value); if present, a mismatch causes rejection.

```json
{
  "schema_version": 3,
  "catalog_version": "2026-10-09.f085e40b",
  "sha256": "<content-sha256-optional>",
  "series": [
    {
      "name": "vLLM · CUDA",
      "engine": "vllm",
      "purpose": "inference",
      "framework": "cuda",
      "versions": [
        {
          "name": "cuda13.0-vllm0.30.0-r2",
          "image_ref": "gpuworks/gpuworks-runner:cuda13.0-vllm0.30.0-r2",
          "engine_version": "0.30.0",
          "framework_version": "13.0",
          "arch": "multi",
          "registry_sources": [
            "quay.io/gpuworks/gpuworks-runner:cuda13.0-vllm0.30.0-r2",
            "swr.cn-southwest-2.myhuaweicloud.com/gpuworks/gpuworks-runner:cuda13.0-vllm0.30.0-r2"
          ],
          "notes": "..."
        }
      ]
    }
  ]
}
```

Each series must have at least one version. Both `image_ref` and `registry_sources` must include tags; digests are not accepted. `image_ref` must be unique across the file.
The legacy fields `run_spec`, version-level `command_mode`, series-level `vendors`, and version-level `supported_gpus`/`unsupported_gpus`
are ignored during import: the image catalog does not carry launch configuration (ADR 0031), and the vendor is derived from `framework`.

## Community Images

The Add Community Image drawer on the Community tab lists built-in community repository cards (`GET /api/v1/images/community/repos`):

| Repository | Registry Type | Engine / Framework |
|---|---|---|
| `vllm/vllm-openai` | Docker Hub | vllm / cuda |
| `vllm/vllm-omni` | Docker Hub | vllm-omni / cuda |
| `lmsysorg/sglang` | Docker Hub | sglang / cuda |
| `quay.io/ascend/vllm-ascend` | quay | vllm / cann |
| `quay.io/ascend/sglang` | quay | sglang / cann |
| `harbor.sourcefind.cn:5443/dcu/admin/base/vllm`; the same card also includes `…/custom` and `…/sglang` | OCI distribution | vllm / dtk |

When you open a card (or enter any repository), `GET /api/v1/images/community/browse?repo=<repository>` lists **all** upstream
tags for that repository without semver filtering. Tags such as `vllm/vllm-openai:qwen38` are also selectable. The frontend supports searching by name.

- Docker Hub and quay tags include the upstream update time (`last_updated`); OCI tag lists do not include timestamps.
- For unconfigured repositories, the type is inferred from the host: no hostname means Docker Hub, `quay.io/` means quay, and all others are treated as OCI distribution.
- When an OCI repository returns 401, an anonymous token is acquired using the Bearer challenge, and the request is retried once. If it still returns 401, the error is `community registry requires credentials`;
  private repository credentials are not currently supported.
- Pagination is limited to 10 pages, with an 8-second timeout per page request. Results are cached in memory for 1 hour and are not persisted in the database. Tags that disappear upstream during the cache period are marked
  `upstream_gone` in the response.
- The `image_community_catalog` setting can override or append cards. See the [configuration reference](configuration.md#镜像目录与镜像拉取).

After selecting a tag, complete the framework, version, and other fields in the same drawer and add it to write it to the catalog (`source=community`). Browsing alone does not write to the database.

## Custom Images

Custom images accept any reference with a tag. The engine dropdown comes from `GET /api/v1/images/engines`: all deployment engines (`vllm`, `sglang`, `callable`)
plus the catalog-only `vllm-omni`. The server provides the values, order, and display names. Framework is required; images without a framework do not participate in automatic image selection. Custom images registered as `callable`
are visible when you select the callable engine on the deployment page. The callable engine does not provide its own command line ([ADR 0036](../adr/0036-callable-command-owned-by-template.md));
without an inference template, you must enter the adapter's complete command in the deployment command editor. You can also paste a `docker save` archive URL in the add drawer to resolve the actual reference first.
See [Importing from an HTTP File Server](../how-to/import-from-http.md#从-url-导入镜像归档).

Adding either community or custom images uses the `{"series":[...]}` form of `POST /api/v1/images/import` (without `schema_version`);
this form cannot write `source=official`.

## Rolling Tags

`latest`, `main`, `master`, `release`, `nightly`, `dev`, and `edge` (whole-tag, case-insensitive matches) are rolling tags,
whose content changes with upstream updates:

- Automatic image selection (when no image is explicitly specified for a deployment) never selects rolling tags. Manual selection is unrestricted.
- The node distribution table shows each node's 12-character image digest and update time. If the same version has different digests across nodes, the details show a notice.
- A pulled rolling-tag version has a “Pull again” action on its node row (`POST /api/v1/images/{id}/nodes/{uuid}/sync` with `"force":true`):
  it actually pulls again even if the image is already `present` on the node, and writes back the new digest afterward. No duplicate transfer starts while the node is `pulling`/`syncing`.
- Deployments do not force a re-pull just because a tag is rolling, and existing digests on the node are not cleared.

## Automatic Image Selection, Pull Addresses, and Command Modes

Series do not have a dedicated default field. After matching vendor, framework, engine, architecture, and chip family, automatic deployment selects the latest
version among enabled, non-deprecated versions with non-rolling tags. The driver/framework compatibility matrix is used only for ranking and warnings; it cannot replace actual hardware facts and does not prevent you from explicitly selecting an image.
The chip family is derived from the Ascend model segment of the tag (`910b` is the 910B series, `a3` is 910C, `310p` is 310P); on the node side it is the family detected for the selected (or first) card.
An image whose family is known and differs from the node's (for example the `a3` build on a 910B4 node) is neither picked automatically nor listed among the selectable images; specifying such an image manually is rejected as an image incompatible with the node.
Generic images without a model segment, and nodes whose chip family is not yet recognized (including `950` cards for now, whose family exists only once their chip identity is detected), never trigger this exclusion.
When the catalog has no candidates, non-NVIDIA nodes do not incorrectly fall back to the CUDA profile's default engine images (`vllm/vllm-openai:latest`,
`lmsysorg/sglang:latest`). You can explicitly override the image.

`image_ref` is the canonical reference (the Docker Hub address). [Pull settings](../how-to/configure-pull-settings.md) determine where nodes actually pull from:
alternative addresses generated by source rules applicable to the node come first, followed by `registry_sources` and the canonical address, ranked by reachability on the node. After pulling, the image is locally
tagged back to its canonical reference, so the meaning of `image_ref` remains unchanged. See [Troubleshooting](../how-to/troubleshooting.md#镜像拉取失败) for candidate ordering.

In the default engine-controlled command mode, Docker, runveil (the `udocker` driver), and nerdctl all override the image's default entrypoint
and append the actual arguments, avoiding duplicate execution of vllm serve or tini --.

Command mode is selected explicitly only by the deployment (engine-controlled by default) and does not change with the image source or
image catalog. The image catalog provides only the framework, versions, and acquisition addresses, not launch configuration (ADR 0031). You can inspect the image's own ENTRYPOINT/CMD/ENV
on a node from the image details.

Facts such as GPU model and compute capability come from node detection; the image catalog does not maintain free-text compatibility tags.
See [Deployment Launch Parameter Sources](deployment-launch-sources.md) for the source of each launch field.

runveil (the `udocker` driver) creates a canonical ROOT loopback for every container (so proot guests can resolve host paths leaked by `/proc/self/maps`).
Only NVIDIA containers additionally set TRITON_LIBCUDA_PATH, FLASHINFER_DISABLE_VERSION_CHECK, and
SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK. These variables address only library discovery and version checks; they do not bypass NCCL safety checks. See the architecture documentation for the full
runtime explanation.
