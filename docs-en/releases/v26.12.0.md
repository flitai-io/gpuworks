# v26.12.0

Released 2026-11-26 · Release line 26.12 · Commit `92ffae740`

The first release of the 26.12 line. Compared with v26.11.4, this release connects whole Kubernetes and Slurm clusters, adds AMD and Kunlunxin accelerators,
introduces request priority, and makes the `/v1` inference gateway require an API key by default. It includes database migrations; read the upgrade notes below before upgrading.

## Upgrade Notes

- **This release migrates the database, and a 26.11 binary cannot simply be put back afterwards**: migrations run when the new server first starts and only go forward; there is no reverse migration. An upgrade backs up the main database, configuration, `master.key` and the old binary automatically,
  back up the data directory yourself before replacing the binary by hand. To return to 26.11, restore the backup taken before the upgrade as described in [Upgrades and Version Compatibility](../how-to/upgrade-and-compatibility.md#回滚).
  The backup does not hold the statistics database `stats.db`, and this release changes its structure: after the restore a 26.11 server refuses to start with `stats.db was written by a newer release`. With the server stopped, move `stats.db` (and its `-wal` and `-shm` files) out of the data directory and keep them, then start.
  The older server creates an empty statistics database: the GPU utilization and card time history in Usage analytics, and the history older than 24 hours in Scheduling analysis, are no longer shown; service quality in Usage analytics is filled in again for the days the request observation database `ux.db` still holds; token usage per token lives in the main database and is unaffected.
  The automatic rollback after a failed upgrade does not handle `stats.db` either: once the new version has started, the restored older version needs this step before it can start.
- **`/v1` requires an API key by default**: a request without a key gets 401, also when the database holds no key at all. Installations that deleted every key and relied on keyless access must create a key after upgrading,
  or have an administrator turn on "Accept /v1 inference requests without a token" (`inference_open_access`) under **Settings → Security**. A new server no longer creates a `default` token. See [OpenAI-Compatible Gateway](../reference/openai-gateway.md#认证).
- **Upgrade the server first, then the agents**: copies relayed through the management node and start stall detection need agents on this release too.
  After the server upgrade, **Version and updates** shows below the Server row how many online nodes are on another version; select **View compute nodes** to open the filtered node list and upgrade them in a batch.
- **A control plane that an older installer placed in `/opt/gpuworks` needs root for a command-line upgrade** (`sudo ./gpuworks upgrade`): the upgrade first makes that directory root-owned.
  Without root the command refuses and prints the command to run. After the migration the service account can no longer replace the binary in that directory, so the console upgrade of such an installation shows as unavailable (`not_writable`) and every later upgrade uses `sudo /opt/gpuworks/gpuworks upgrade`. See [Control Plane Installation Layout](../reference/install-layout.md#控制面装在-agent-共享根目录时).
- **Request priority is on by default only for new deployments**: deployments created before the upgrade stay off; turn it on in the edit form when needed. Changing the switch rebuilds the replicas.
- **Administrator passwords must now be 8–128 characters**, and common passwords, whole-value repetition and sequences are refused. The rule is checked only when a password is created or changed; existing accounts sign in as before.
- **Permissions on credential files are tightened**: startup, install and upgrade change existing sensitive files to owner read-write only (`0600`). They are opened to the trusted service group (`0660`) only when the systemd unit's group is the default credential group, or an older unit runs as the default service account; installations with other custom accounts stay at `0600`.
- **Card health codes are now upper case**: a migration rewrites `gpus.health_code` and the reason code of card health records from lower case to UPPER_SNAKE, and `health_code` in API responses changes with it. Scripts or alert rules that match the old lower-case values need changing.
- **Sync groups with the same name are renamed**: sync group names must now be unique. On upgrade, existing duplicates get a suffix by ID; group IDs, node conditions and rate limits are kept.
- **Sites that connected a Kubernetes cluster with a nightly build must apply the manifest once more after upgrading the server** (`kubectl apply` or "Apply to the cluster"): the agent's Pod then shares the default mount directory `/mnt/gpuworks` with its node.
  Until it is applied, NFS storage with a mount point under that directory reports on those nodes that the agent does not share the directory with its node, and nothing is mounted. See [Connect a Kubernetes Cluster](../how-to/connect-kubernetes.md).

## Added

### Clusters and Node Onboarding

- **Connect a Kubernetes cluster**: an existing containerd cluster joins through a DaemonSet, and one cluster entry can cover NVIDIA, Ascend, Hygon, PPU, AMD and Kunlunxin nodes together;
  whole-card deployments are supported, with dGPU as well on NVIDIA, Ascend, PPU and AMD (Hygon and Kunlunxin are whole-card only), and cards can be borrowed through HAMi and Alibaba Cloud ACK GPU sharing. See [Connect a Kubernetes Cluster](../how-to/connect-kubernetes.md).
- **Connect managed Kubernetes from a public cloud**: Alibaba Cloud ACK, DigitalOcean DOKS and Nebius mk8s have been tested. ACK and DOKS clusters can also be connected from the cloud account and applied and removed in the console with a checked plan, provided the cluster's API server has a public address; on Nebius the manifest is applied with `kubectl`.
  See [Connect Managed Kubernetes from a Public Cloud](../how-to/connect-managed-kubernetes.md).
- **Connect a Slurm cluster**: run the onboarding command once on the controller node and the GPU compute nodes install the agent themselves; cards stay allocated by Slurm and a deployment borrows them with a placeholder job. Only NVIDIA cards are supported for now,
  and an Alibaba Cloud E-HPC cluster can be connected straight from the cloud account. See [Connect a Slurm Cluster](../how-to/connect-slurm-nodes.md).
- **DigitalOcean**: a new cloud account type that syncs GPU Droplets and DOKS clusters. See [Rent Cloud GPUs](../how-to/rent-cloud-gpus.md).
- **ZStack Cloud**: the legacy and intermediate Cloud GPU protocols are supported, with 4.8.0 as the minimum version. See [Onboard ZStack Cloud](../how-to/onboard-zstack-cloud.md).
- **Nodes behind NAT**: when two nodes cannot reach each other, model and image copies can be relayed through the management node; the relay's rate limit and timeouts are set under `peer_relay` in `server.yaml`, and its concurrency is fixed. See [Sync Models and Images Between Nodes](../how-to/peer-sync-models.md) and [Peer Relay Resource Limits](../reference/configuration.md#节点间中继的资源限制).
- **Connection evidence**: when a node stays connecting or goes offline, an administrator can select **Check connection** under Connection evidence in the node details to read read-only evidence, without the control plane needing SSH to the node.
- **The External Platforms page**: cloud accounts and Kubernetes and Slurm cluster entries are all added and managed on the External Platforms page under Compute.
- **Documentation**: [Run GPUWorks on Windows WSL2 with Docker](../how-to/wsl2-with-docker.md) is new.

### Accelerators

- **AMD (ROCm)**: whole-card deployments on Docker, nerdctl, runveil and Kubernetes on Linux amd64, tested for single-GPU BF16 text inference on MI325X (gfx942) and AMD395 (gfx1151); other combinations still need per-profile validation. Multi-node and PP were tested on two MI325X hosts, and vLLM sleep/wake and PD (`vllm-nixl`) on MI300X. dGPU provides a user-space hard memory limit (experimental, with no compute limit). The built-in `rocm7.2.3-vllm0.30.0-r1` image and Qwen3 specs for gfx942 and gfx1151 are included.
- **Kunlunxin P800**: whole-card deployments on Docker, nerdctl and Kubernetes on Linux amd64. The platform offers TP, PP, engine DP and multi-node TP, and does not offer PD, partitioning or sleep. Only a single card has been tested (production start, chat through the gateway, and a single-card deployment on a Kubernetes node); several cards on one host were blocked by an XRE initialization error in the test environment and cross-node was not tested, so multi-card and cross-node are not yet accepted. See [Kunlun P800 Deployment](../how-to/kunlun-p800.md).
- **NVIDIA unified-memory cards**: RTX Spark and Thor are recognized beside GB10; when `nvidia-smi` reports no used memory, the used amount is measured from the host's memory pool too. Thor has not been verified on hardware.
- **PD disaggregation on Hygon and PPU**: the `vllm-mooncake`, `sglang-mooncake` (Hygon, unverified), `sglang-ppu-ipc`, `sglang-ppu-mooncake` and `vllm-ppu-mooncake` modes are new. See [PD Disaggregation Deployment](../how-to/pd-disaggregation.md).

The validation status of each combination is in the [Vendor Support Matrix](../reference/support-matrix.md).

### Deployment and Inference

- **Request priority**: engines queue requests by priority, and only the gateway decides it, from the priority class bound to the API token and the `X-GPUWorks-Priority-Class` request header. See [Request Priority](../explanation/request-priority.md).
- **Save a deployment as an inference template**: export importable YAML and a test record from a running deployment. See [Save a Deployment as an Inference Template](../how-to/save-deployment-as-template.md).
- **Hand-written launch commands for multi-node and PD deployments**: click **Edit Command Text** in the command preview and start from the script the server generated.
- **KV offload backend**: a deployment chooses a KV offload backend per engine; vLLM has two built in, `native` (the default) and LMCache.
- **Template capabilities**: a template can declare managed writable directories (`dirs`), let each rank download and mount its own weight subfolder, and serve engine metrics on a second port.
- **System One decision endpoint**: the gateway adds `/v1/systemone`, and deployments that serve it can be health-checked.
- **MinerU**: a built-in MinerU2.5 vision model template that works with the MinerU client to parse PDFs. See [Connect MinerU to a remote vision model](../how-to/use-mineru.md).
- **The built-in catalog** grows to 405 models (392 in v26.11.4), adding SenseNova-U1.6-8B-MoT, Kunlunxin Qwen specs, Strata GGUF specs, and DeepSeek-V4.1-Flash on two and on four DGX Spark.

### Images, Monitoring and Operations

- **Image import**: under an image's Node Distribution, set a node's Acquisition Method to "Import from node file…" to load a tar archive that is on that node; Docker and nerdctl images a node already has can be imported too.
- **Benchmarks**: the results page gains an interactive request timeline, viewable by session, turn and attempt; and a new **Request timeout**, 600 seconds by default and settable from 10 to 7200 seconds.
- **Start stall detection**: after creating a container the agent observes its output, the card's memory and utilization, and the activity of the container's processes once a minute; when none of the three has changed for 20 minutes in a row the start is failed with `ENGINE_START_STALLED` and rebuilt under the retry rules, without waiting for the start timeout. It applies only to single-node instances on Docker and runveil.
- **Stall reports**: when a log write or a store operation on the server waits longer than `log.stall_report_after` (3 seconds by default), the live stacks are recorded. See [Troubleshooting](../how-to/troubleshooting.md#server-卡住或偶发变慢时卡顿报告与现场堆栈).
- **Change password**: choose **Change password** in the account menu at the top right of the console; all sessions of that account are signed out afterwards.
- **Plugin packages**: the new `gpuworks plugin` subcommands verify, install and remove signed plugin packages; the wire formats are in [Plugin Protocol and Wire Formats](../reference/plugin-protocol.md).

## Changed

- A server upgrade picks a specific version under **Version and updates**: the same channel lists the installed version and later ones, searchable by version or commit; a branch build the channel never published is no longer shown as up to date.
- The node list shows the Agent version by default and marks nodes that are pending upgrade, pending alignment or on a different build. A node whose upgrade timed out is recorded as unconfirmed and stops holding the upgrade slot after 5 minutes.
- Errors the gateway itself returns all have the OpenAI shape with a stable `code`; `GET /v1/models` lists only the served names that can be routed right now, and a scoped key sees only the deployments it may call.
- When the server stops normally, requests waiting for a sleeping deployment to wake get 503 `SERVER_RESTARTING` with `Retry-After: 10`.
- A failed start shows what the container printed before it exited and the exception the engine process raised; install, recovery and runtime failures show their cause by a stable code.
- Once scheduling is enabled on a card by hand, the decision stays in force; later reports from the card and server restarts do not end it.
- The Vast.ai integration is updated. (GWKS-348)
- The build toolchain moves to Go 1.26.11.

## Fixed

### Upgrade and Install

- A database upgraded from the benchmark history database of v26.11.0–v26.11.2 lacked columns in the image series table, so the server failed while syncing the image catalog at startup and did not come up. The two migrations are now applied in their original place at startup. (GWKS-241)
- On a control plane installed as root and run by a service account, the console's online upgrade and uploaded upgrade always rolled back: the upgraded process could not write the `install-history.jsonl` root had created and was taken for unhealthy. The file is now handed to the service account at install, and a failed write is only a warning; an installation already affected is repaired by running `gpuworks upgrade` once as root. (GWKS-247)
- A control plane installed directly in `/opt/gpuworks` could not be uninstalled: the uninstall was refused before it began. It can now be uninstalled, and the shared agent root is kept. (GWKS-198)

### Deployment and Scheduling

- When a dGPU memory limit was too small for an instance to start, only the engine's own error was shown and nothing said the limit was the cause. vLLM's startup check, PyTorch's out-of-memory error, the Ascend vcann-rt refusal and a KV cache that does not fit the limit now all list `DGPU_MEMORY_LIMIT_EXCEEDED` among the instance's failure causes;
  the instance's own error code is still `CONTAINER_EXITED`. (GWKS-423)
- After one partition on a shared Ascend card failed to start, the platform ran the runtime check on the whole card at once while other partitions were serving on it; the failed check marked the whole card unschedulable until it was free. The check after a failed start now leaves out cards other instances are serving on. (GWKS-425)
- A sleepable vLLM deployment on a Hygon node without enough host memory was killed during engine start (`EngineCore -9`): on Hygon the sleep memory pool is backed by host RAM.
  Creating or evaluating such a deployment is now refused with `SLEEP_HOST_BACKING_INSUFFICIENT`, naming the memory needed and available. (GWKS-428)
- A sleepable vLLM deployment in an 8 GiB Ascend dGPU partition exited at every start with `NPUCachingAllocator` error 300000. The default `gpu_memory_utilization` of a sleepable Ascend partition is now measured against the memory limit (0.75 for an 8 GiB limit);
  the new default has not been run on the hardware. (GWKS-427)
- A manual command written as a shell script bypassed topology validation: `--tp-size 1` was accepted on a two-card placement and the second card sat assigned and idle. A script is now held to the assigned card count too. (GWKS-415)
- A deployment with TP=1 and DP=2 was assigned one card and then refused at launch validation. Cards are now allocated for the engine's data-parallel replicas.
- When a runveil workload stopped, it was reported removed before its killed engine processes had released the card, so the leftover process counted as use outside the platform; after a deployment was deleted the card stayed unschedulable for three to four minutes. Removal is now reported once the killed processes are gone, and the card is free at once. (GWKS-432)
- A multi-card Ascend start on runveil passed logical device IDs in the order the cards were selected; on hosts where logical and physical order differ the ACL runtime refused the list with EE2002 and the start exited at once. They are now passed in ascending order. (GWKS-418)
- The automatic runner image pick gave a 910B4 node the A3 (910C) build. The pick now follows the node's Ascend chip family.
- The fp8 KV cache rule matched every model type containing deepseek, so DeepSeek-OCR-2 was started with `--kv-cache-dtype fp8` on a PPU and its first request failed. The rule now applies only to DeepSeek's MLA models. (GWKS-493)

### Models, Images and Storage

- A model copy on a node's own disk that was deleted by hand, or lost when the node was reinstalled, stayed recorded as present: a deployment failed its launch on the missing directory three times and stopped, and the node never fetched the model again.
  The pre-start check now reports the missing directory as `MODEL_PATH_MISSING`, the server takes the record back, and the next attempt acquires the model first. Records on shared storage are unaffected. (GWKS-517)
- One 429 from a model source failed the whole download within milliseconds, and the deployment stayed blocked until someone retried by hand. A 429 or 503 is now waited out for the time the source names and retried, with the status showing the source's rate limit. (GWKS-272)
- A model download that gave up after its last address kept dropping the connection deleted the part already downloaded and its resume state, so the retry began again. They are now removed only when the fetch moves to another address. (GWKS-447)
- Different revisions of one model were written into the same directory on a node. Automatic transfer directories are now kept apart by revision. (GWKS-281)
- After switching NFS with local cache to NFS, nothing cleaned the cache directories on the nodes and they stayed for good. The switch now clears each node's cache first and is refused with `STORAGE_CACHE_NOT_EMPTY` while any remains. (GWKS-242)
- On a large NFS share, a storage scan page that found no model before its deadline returned the same cursor and the scan stayed where it was. Every page now moves forward. (GWKS-413)
- After one call hung on a hard NFS mount, the storage stayed unresponsive on that node until someone ran `umount -f -l` and restarted the agent. On an NFS mount the agent created, a single call blocked for 3 minutes now gets the mount forced off and mounted again. (GWKS-383)
- The periodic image inventory did not report the runtime image identity, so offline deployments lacked it. (GWKS-238)
- A forced re-fetch of an image a node already had failed, and seconds later the periodic inventory set the state back to present and cleared the failure. The failure and its cause now stay visible. (GWKS-246)

### Node Onboarding and Accelerators

- A manually registered node has no saved SSH credentials, yet removing it still attempted an SSH uninstall and failed, so the node could not be removed. A node without saved credentials now has only its record removed, which the confirmation states beforehand. (GWKS-228)
- On hosts that accept a password only through keyboard-interactive, SSH onboarding failed and showed only the library's raw error. The onboarding wizard now supports this method. (GWKS-205)
- A second host behind the same gateway or NAT address, differing only in SSH port, was refused at onboarding with `NODE_INSTALL_HOST_ALREADY_NODE`. Hosts are now matched by SSH host and port.
- A node the server dials stayed in connecting after its probe ended, with no way to reconnect. It can now be reconnected by hand. (GWKS-230)
- NVIDIA cards bound to the nouveau driver were shown as held outside the platform instead of missing the vendor driver. (GWKS-412)
- When a dGPU probe returned nothing, the server asked for an agent upgrade instead of giving the real cause. (GWKS-429)
- RoCE ports whose IPv4 address sits on a bridge, bond or VLAN reported `no_ipv4` and were left out of network planning.
- When a ZStack Cloud host did not meet the conditions, installing the agent reported only a generic error. It now states the reason.

### Built-in Templates

- The Turing specs of DeepSeek-OCR and DeepSeek-OCR-2 never started because vLLM 0.31 refuses the built-in n-gram logits processor; they now select the V1 runner (`VLLM_USE_V2_MODEL_RUNNER=0`). Not yet run on a Turing card. (GWKS-485)
- The `--chat-template` path of four PPU specs did not resolve in the PPU runner, and three of them failed every start: two wrote the weights' directory as `/models/<org>/<repo>` (the weights are mounted at `/model`), and for the example template the two Gemma 4 specs named it was not checked whether the image carries it elsewhere. All now name the template file in the mounted weights; moving Gemma 4 to the checkpoint's own template may change how tool definitions and tool results are rendered. Not yet run on a PPU node. (GWKS-484)
- The Qwen3.5-27B PPU spec failed to start with the engine's default of 1024 sequences and is now capped at 256. Not yet run on a PPU node. (GWKS-486)
- The PPU spec of LLaDA2.1-mini is removed: the FlashInfer in the PPU runner is older than SGLang's diffusion path requires, so it could not start. The model remains available on NVIDIA. (GWKS-430)
- The ModelScope sources of 19 catalog models were pinned to Hugging Face commits, and downloads returned 404. (GWKS-410)
- With weights downloaded from ModelScope, the HunyuanOCR NVIDIA specs failed in vLLM because the tokenizer lacked `image_token`; that source is removed. (GWKS-436)
- The image of the Hygon Qwen3-TTS spec has no vllm-omni, so the container exited 127; the spec is removed. Three Hygon vision specs pulled a `latest` image that does not exist; their original image reference is restored. (GWKS-374)
- Qwen3-Reranker-8B advertised a chat endpoint that failed and now advertises only rerank; its NVIDIA spec selects SGLang's reranker template. (GWKS-352)
- MiniCPM on Ascend was placed on a single 32 GiB card that cannot hold its initialization peak. Placement now refuses it. (GWKS-351)
- The 910B SGLang spec of Gemma 3 27B crashed at the first generation in graph mode and now runs eagerly. (GWKS-354)
- Chat on the Hygon Qwen3.5-35B-A3B spec returned empty content: the model thinks first, and the thinking is not in `content`. The spec now answers without thinking by default. (GWKS-373)

### Console, Monitoring and API

- The metrics database had a single connection, so metrics reported by agents could not be written while a range query ran; with a longer retention one query could hold writes for seconds. Queries now use a read-only connection pool. (GWKS-240)
- Non-streaming benchmark requests carried `stream_options`, and strict OpenAI-compatible servers answered 400. (GWKS-330)
- A personal inference key could not read batch jobs the same user created in the console. (GWKS-317)
- The AI assistant's node inspection failed when its jq filter did not match. It now still returns the body and the reason. (GWKS-239)
- Exported log CSV files had no BOM, so Chinese text was garbled in Excel. (GWKS-367)
- A sync group rate limit entered as 0 was silently saved as 0.01 MB/s. The value is now refused. (GWKS-297)
- After a live log stream was refused, the panel stayed on waiting for logs. It now shows why the stream was refused.

## Security

- Whether `/v1` accepts a request without a key is now an explicit security setting, off by default, and no longer depends on whether the database holds a key; when the setting cannot be read it is treated as off.
- The plugin host new in this release uses `golang.org/x/net` v0.60.0, in which GO-2026-6603, GO-2026-6610, GO-2026-6611, GO-2026-6612 and GO-2026-6617 in the HTTP/2 implementation are already fixed. The 26.11 releases have no plugin host and do not depend on this library, so they are not affected. (GWKS-419)
- Built with Go 1.26.11, fixing GO-2026-6859 in `net/http`: a request body limit racing with response header writes could panic. (GWKS-233)
