# ADR 0083: Busy Rejection: a Gateway in Front Declares "Don't Queue If Busy", and GPUWorks Decides at Admission

Date: 2026-11-26 · Status: Accepted

## Background

Some sites put another gateway in front of GPUWorks, with other upstreams (a public cloud, for example) behind the same model name. That gateway wants to send requests elsewhere while local capacity is short, and to come back as soon as local capacity frees up.

The industry's AI gateways all divert after failure: they wait for a 429, a 5xx or a timeout before trying another upstream. GPUWorks never refused a request for being busy. When the replicas were full the request queued in the engine, and the gateway in front could only wait for a timeout or estimate on its own how busy GPUWorks was.

The gateway in front also needs to know which priority classes the API key it uses can reach in GPUWorks, and which models schedule by priority, to decide how to send `X-GPUWorks-Priority-Class`. Only the management plane showed this.

## Decision

1. **The caller declares; GPUWorks decides at admission.** A model request with `X-GPUWorks-If-Busy: reject` says "don't queue if busy". When GPUWorks judges that it cannot take the request now, it answers 429 `MODEL_BUSY` at once, with `Retry-After: 1`; when it can, it forwards the request as usual. Only the value `reject` is a declaration; any other value is the same as no header, and the header never reaches an engine. A request without the declaration behaves exactly as before. Whether it is worth going to another upstream to avoid queueing stays the gateway in front's decision, because only it knows whether it has other candidates.
2. **The contract is the semantics; the rule is internal.** Callers recognize a rejection by the status code and `error.code` only, do not match `message`, and do not depend on how "cannot take it" is worked out. The rule may become more precise later (for example covering cases that are not rejected below, or summing across servers) without changing the semantics or the interface.
3. **The first version's rule: no eligible replica has a free run slot.** A replica's run slots are the concurrent-sequence limit stated explicitly in its instance's launch arguments (vLLM `--max-num-seqs`, SGLang `--max-running-requests`, `max_num_seqs` in the parameter dictionary), read by `deploy.RunSlots`. A replica has no free slot when the requests in flight on it that this request would wait behind reach its run slots: on a replica that schedules by priority (its instance was launched with priority scheduling and the gateway writes the engine's `priority` to it) those are the ones at this request's priority value or above, and lower ones do not count; any other replica runs requests in arrival order, so every request in flight counts. When the replica the deployment's routing policy prefers is full and another eligible replica has room, the request goes to the one with room.
4. **Judging and taking a slot are one step.** The check runs under the replica selector's lock, before the lease is taken (`balancer.hasRoom`), so two concurrent requests never both get the last free slot. In-flight requests are counted per priority (`inflightCounts`), and a released lease gives back the class it was taken at.
5. **When unsure, do not reject.** These cases are forwarded as usual or handled by the existing rules: a deployment with a running replica whose run slots are unknown (its launch states no limit, the value is not a positive integer, the value is one the shell still expands, or the data-parallel size is not 1), judged for the deployment as a whole whichever replicas are left to choose from, as `/v1/key` reports with `busy_reject: false`; PD-disaggregated deployments, multi-node deployments, a deployment that is asleep or waking, a resend to another replica after a connection failure, a replay after preemption, and auxiliary routes such as `/v1/tokenize` and the playground (the declaration is dropped).
6. **A rejection is not one of the deployment's requests.** It is counted in the 429 class of the deployment's gateway requests, leaves no request record and does not update the deployment's last request time. The error's `type` is `invalid_request_error`: the gateway's error table uses `server_error` only for 5xx.
7. **The key information endpoint.** `GET /v1/key`, authenticated with an API key (as `/v1/models` is), returns: the gateway features this server supports, `features` (`priority_scheduling_header`, `busy_reject`; only ever added to); the key's priority binding, `priority` (`own`, `ceiling`, `reachable`; `null` for anonymous access), worked out by `priority.KeyReach` with the same rules as `Resolve`, so a caller needs only one rule: "the named class if it is in `reachable`, otherwise `ceiling`"; and, for each model the key may call, `priority_scheduling` (`all`/`some`/`none`) and `busy_reject` (whether it can be rejected). It is answered from the route table and the priority class snapshot, reads no deployment rows and is not inference traffic. The response header `X-GPUWorks-Priority-Scheduling: on|off` says whether the engine scheduled this request by its class.
8. **With several servers, each counts its own.** In the first version the in-flight counts are the lease counts inside each server process and are not summed across servers. The result is an undercount: a server may fail to reject when it should, and never rejects wrongly.

## Trade-offs

- **Having the gateway in front poll load and divert in proportion to queue depth (rejected).** An engine's queue length updates with the metrics collection interval and is seconds old or more when it reaches the gateway; diverting in proportion to stale numbers oscillates. Queue length is decoupled from capacity: a deployment with a large concurrent-sequence limit can be overloaded with a queue length of 0. Drawing lots per request would also push sessions in progress to another upstream turn by turn. GPUWorks's in-flight counts are live, and deciding at admission has no control loop and so no oscillation.
- **Carrying load in every response header (rejected).** Once traffic has been diverted, the gateway cannot see when local capacity recovers; at saturation the first byte is slowest, so the header is stalest exactly when it is most needed.
- **Judging by the total in flight on a replica that schedules by priority (rejected).** Such an engine runs higher-priority requests first, so queued requests of a lower priority are not a wait for this request. Judging by the total, a queue full of low-priority batch work would push normal requests away for nothing. A replica that does not schedule by priority runs requests in arrival order, where the total is this request's wait, so it is judged by the total.
- **Never rejecting high-priority requests (rejected).** By the rule in item 3, a high-priority request is rejected only when requests of the same or a higher class fill the run slots, and staying local would only queue it behind its peers. Whether data may leave the site is expressed by the gateway in front's rules, not by priority.
- **Using the engine's default when run slots are unknown (rejected).** GPUWorks does not know each engine build's default, and a wrong guess costs wrong rejections. A deployment that states no limit has `busy_reject` `false` in `/v1/key`, so the gateway in front knows the declaration has no effect on it; once there is a reliable way to judge it, only that model's `busy_reject` turns `true`.
- **PD-disaggregated and multi-node deployments never reject.** Their run slots cannot be counted from one replica's leases; judging by one phase or one rank would reject wrongly.
- **No summing across servers in the first version.** Summing needs a live channel between servers or the engines' reported queue lengths, and the latter lag with collection. An undercount only lets a request queue as usual, the same as without this feature.
- **No request record for a rejection.** A rejection happens within milliseconds and never reaches an engine; the gateway in front has the attempt in its own call records, and GPUWorks's 429 count is enough to see how many there were.
- **Older servers have no `/v1/key`.** They treat the path as a model request with no model and, with a valid key, answer 400 `MODEL_REQUIRED`, not 404. The gateway in front should treat any non-200 other than 401 and 403 as "not offered". Older servers do not know `X-GPUWorks-If-Busy` and forward as usual, behaving as before.

## Consequences

- The gateway in front can divert at once when there is no local room, and new requests come back as soon as there is, without polling.
- To take part in busy rejection, a deployment's launch arguments must state the concurrent-sequence limit. The setup steps are in [Request Priority](../explanation/request-priority.md#connecting-an-upstream-gateway) and the interface in [OpenAI-Compatible Gateway](../reference/openai-gateway.md#busy-rejection).
- Replica choice is unchanged: priority is used only to judge whether there is room, not to choose a replica, and a request without the declaration takes the same path as before.
- Changes to the rule (summing across servers, covering deployments whose run slots are unknown) do not change the interface, only the values of `models[].busy_reject` and when rejections happen.
