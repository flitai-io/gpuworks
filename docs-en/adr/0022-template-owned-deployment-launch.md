# ADR 0022: Templates and Explicit Choices Determine Deployment Launch Configuration; the Image Catalog No Longer Provides an Editable Default Layer

Date: 2026-09-19 · Status: Accepted; "existing deployments retain image defaults" and the `launch_contract` marker are superseded by [ADR 0031](0031-image-catalog-carries-no-launch-config.md) (under the authorization for this deployment-page design and implementation; supplements ADR 0020, supersedes ADR 0013's selection of the default command mode by image source, and supersedes the part of ADR 0019 where new deployments read image runtime defaults)

You may enter an RTX-specific image, a medical-model-specific image, or a private image directly. Parameters, environment, preparation scripts, and runtime assets for specialized models belong in inference templates; you can override them or take over the command directly. The image catalog no longer maintains another configuration that implicitly rewrites new deployments. Otherwise, editing the image catalog after evaluation could cause the same deployment to run a different command at initial startup or rebuild, violating the promise that what you see is what runs.

For new deployments, the engine dictionary, selected template, and your current input determine launch configuration through the existing Materialize / ResolveLaunch pipeline, and the result is saved in existing deployment fields and the selection snapshot. The default command mode is `engine`; `image-entry` and `manual` must be explicit choices for this deployment. Changing the image or switching form views does not change that choice or reapply environment variables, mounts, or launch commands from the image catalog. Custom images do not require prior registration; unknown compatibility produces only a notice, while known resource and placement conflicts must still be rejected.

Images remain runtime artifacts. Engine versions, frameworks, architectures, acquisition addresses, and actual OCI ENTRYPOINT/CMD/ENV are image facts; this decision does not change how the container runtime consumes them. OCI contents that have not been read must display as unknown, and configured environment variables must not be presented as the final process environment that includes the image's built-in environment. Inference templates store knowledge about models and specific software/hardware combinations. Engine dialects and launch adaptation belong to the respective engine modules—for example, SGLang's logging environment and preparation scripts—and are not reimplemented in the API, generic deployment flow, or frontend.

To prevent upgrades from changing existing launch semantics, the existing selection snapshot records a launch-contract marker. Only the new contract stops reading the editable image default layer; existing deployments without the marker retain their original semantics. The marker identifies only the interpretation version and does not store another editable configuration. Migrating existing deployments requires separate verification; adding a marker must not change their startup behavior.

The cost is that new deployments can no longer rely on configuration once implicitly injected by the image catalog; that configuration must be explicitly written into the template or the current deployment. Old image catalog fields remain for compatibility with existing deployments. Keeping dynamic default merging would leave launch results dependent on mutable external state, so this alternative is rejected.

## Consequences (2026-09-22 Addendum)

- **Typed selection snapshots**: a deployment's selection snapshot (`deployments.template_snapshot`) is represented by a single type, `deploy.CatalogSelection`, whose field tags are shared by the writer and all six read sites. Previously, each read site decoded independently, so a new template field could reach five sites and miss the sixth. Now unknown keys remain in `Extra`, and re-encoding stored rows preserves the original bytes (fixtures `internal/server/deployment/testdata/catalog_selection_{template,custom_model}.golden`). The snapshot remains a historical record, not a configuration that can be recalculated.
- **Recheck GPU predicates in existing snapshots**: deployments with the `launch_contract` marker interpret snapshots according to this ADR's launch semantics. However, on every rescheduling, the snapshot's `gpus`/`unsupported` predicates are rechecked against current cards for **all** deployments, including existing rows without a marker. Mismatches record `placement_rejected` and reject startup. This safety property is introduced in phase 0 and retained: the marker explains only "where launch configuration comes from," not "whether the hardware still satisfies the template." This does change unmarked existing deployments from "start from the old snapshot" to "reject startup after hardware changes," and that change is explicitly recorded here.
