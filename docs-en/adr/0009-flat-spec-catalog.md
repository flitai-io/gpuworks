# ADR 0009: A Flat Spec Catalog Replaces the Five-Layer Evidence Model

Date: 2026-08-30 · Status: Accepted (replaces the five-layer schema in ADR 0007 and the named chip class entities in ADR 0008; retains ideas such as chipmatch predicate evaluation and keeping quantization thresholds in data rather than code. For the full design, see `artifacts/archive/2026-08-24-inference-catalog/plan-template-catalog-v2.md`). 2026-09-15: the args JSON column in decision 7 remains unchanged as the file and storage format. During import validation and deployment, ADR 0020 splits flags defined in the dictionary into fields and passes through those outside the dictionary verbatim; raw argv is no longer used internally for estimation.

## Background

Acceptance testing after deploying the M29 implementation to mirror1 exposed two classes of problems:

1. **Data errors**: the consolidation tool merged entries with identical parameter signatures and ≥2 GPUs. The four Blackwell recipes for B200/B300/GB200/GB300 naturally shared a signature and outvoted the H100/H200 group 4:2, placing `--attention_config.use_fp4_indexer_cache=True` (sm100+ only) and `--moe-backend deep_gemm_mega_moe` (sm90+) in the general-purpose `nvidia_sm75_plus` spec. This guaranteed startup failure on older GPUs, directly contradicting the target of a 95% deployment success rate. Mechanical signature comparison cannot derive a correct general-purpose configuration; a semantic consolidation pipeline is needed (to be designed separately, outside this ADR).
2. **Excessive structural complexity, making the system hard to work with**: the five-layer entities (Template→Variant→ChipSupport→Profile + Evidence/ValidationRun) led to the following: 12,004 evidence entries accounted for 27% of the seed's size, yet the product displayed them only in an internal admin view; ValidationRun had a full schema, validation, DTOs, and UI types, but **0 actual records**; the five flags readiness/support_level/excluded_reason/warn/local_verified came from three different concerns, with no one to fill them in manually; handwritten imports required fabricated three-part evidence bundles and sha256 profile_key values, prompting a dual-format design with a strict internal format and a simplified user format; to cope with catalog granularity, the frontend grew a secondary consolidation list with 40 parallelism flags. Topology facts were stored in two places and already contradicted each other (an A100 spec had tp=1 in its field and `--tensor-parallel-size 2` in args).

An independent internal research infrastructure already holds the authoritative verification facts (a hygon hardware verification ledger with 179 entries containing PASS/FAIL, image digests, and complete argv; an ascend document-mining catalog). The catalog database does not need to duplicate this discipline.

## Decision

Adopt a **flat spec format** derived from gpustack's `model-catalog.yaml`: one format serves internal storage, handwritten user imports, and catalog pipeline output, with no translation layer.

1. **Two-layer structure**: a model entry (model_id, display_title, parameter_count, release_date, context_length) plus a list of specs (spec). A spec contains name, scenario (low latency/balanced/high throughput, optional), engine, image, weights{quantization, sources}, gpus predicates, args, env, and pre_start. weights.sources is a list of download sources (`- huggingface: <id>` / `- modelscope: <id>`), each with its own repo ID; order defines priority, and deployment selects a source based on network reachability and user preference. The three entities Variant/ChipSupport/Profile merge into the single concept of spec.
2. **Use inline predicates for GPU matching instead of named classes**: write `gpus: {vendor, cc: ">=8.9", name: "910[bc]"}` directly on the spec, reversing ADR 0008's named class registry and three-part naming grammar. Its predicate evaluation approach is retained through `chipmatch`, which now consumes inline predicates. Specificity equals predicate narrowness: specific name > narrow interval > open interval. On a tie, the API requires the caller to explicitly provide `template_spec_name`; it must not silently select different weights based on catalog order.
3. **Only two support states**: a matching spec means deployable; a match in the model-level `unsupported` list (gpus predicates + reason + optional quantization constraint) means unsupported, with a reason. “Compatibility reference” entries without complete executable parameters are neither included in the catalog nor displayed. Remove the entire readiness/support_level/excluded_reason/warn/local_verified field mechanism.
4. **Externalize evidence and validation**: remove all Evidence and ValidationRun tables and manifest sections. Traceability remains in the catalog production pipeline's Git artifacts (consolidation decision reports and check ledgers) and the independent verification infrastructure's ledgers. The catalog database stores only facts the product needs to display and use for decisions.
5. **Parallelism is derived at runtime, not stored as catalog data** (as in gpustack): specs have no tp/nodes fields. At deployment, GPU memory estimation determines how many GPUs to allocate, and engine assembly derives `tp = number of allocated GPUs`. Special topologies (pp/ep/multi-node) explicitly specify parallelism parameters in args; when assembly sees an explicit value, it does not derive one. Topology facts have a single source.
6. **Make pre_start first-class**: choose either `pre_start_argv` (a single argv with the same name and shape as the field in the hygon research ledger) or `pre_start_script` (a multiline script that the agent writes to a file, mounts into the container, and executes, with a 64KB limit). An entrypoint wrapper inside the container (`sh -c 'pre && exec engine'`) reruns it on container restart, and it is included in the deployment snapshot. Use custom images for scenarios more complex than a script.
7. **Store data in two tables**: models + specs. Store args/env in JSON columns and use SQL for list filtering.
8. **The static GPU table serves only display and hypothetical planning**: obtain the NVIDIA list from developer.nvidia.com/cuda/gpus, with two classification levels (Data Center | Workstation/Consumer × architecture generation, with the second level derived from CC). List Chinese GPUs (Huawei 310P/910B/910C/950PR/950DT, Hygon K100/K500/BW1000/BW1100, T-Head ZW810E/M890). The table does not participate in matching decisions. “My chips” reads distinct(name, vendor, cc) directly from the GPU table, with no parsing step.
9. **Delete all old assets in one pass, with no transition layer**: the five-layer entities and migrations, chip_classes/chip_registry tables, consolidate v1, frontend substring detection and secondary consolidation logic with 40 flags, and evidence/validation DTOs and UI. The feature is unreleased; discard and reimport the mirror1 data.
10. **Compatibility inheritance across Chinese GPU generations is a catalog production rule, not a matcher rule**: extend the name predicates of specs that PASS on real K100/K100AI hardware to the whole BW family (a bare `BW` that reports only the series, and numbered names such as BW100, BW150, BW1000 and BW1100); extend specs that PASS on real 910B/910B4 hardware to 910C/950DT/950PR. Inheritance comes only from PASS results. An explicit FAIL for the same exact configuration on a successor GPU takes precedence and stops inheritance for that GPU. K500 is outside K100's inheritance scope. Write the expanded scope explicitly into the spec's gpus predicates; chipmatch continues to evaluate data only.
11. **Produce general-purpose NVIDIA specs first, then add dedicated GPU specs and Chinese GPU specs**: in phase one, generate NVIDIA specs model by model from vLLM recipes and the SGLang cookbook. A recipe's tested GPU defines only its verification boundary and does not automatically become a catalog constraint. Luna removes GPU counts, memory utilization settings, length settings, batch settings, and optimizations for the tested GPU from each entry, retaining startup semantics such as parser, dtype, trust-remote-code, and format. This produces general-purpose specs guaranteed to run on at least H20 (CC 9.0), preferably broadening support to A100 (CC 8.0) when there is proof they can run on it. Only specific images that cannot safely support older GPUs, quantization/kernel thresholds, or hardware-specific flags warrant supplemental specs with narrower predicates. Phase two generates Ascend/Hygon specs solely from real hardware test data; do not inflate coverage with documentation claims, a uniform default image, or a uniform parameter template.
12. **A model's date belongs to the original model, not its weight artifact**: `release_date` is the creation date or first auditable release date of the original model repository. Prefer the creation time of the canonical Hugging Face/ModelScope repository. If the repository is not yet public, a release date from a structured recipe at a fixed commit can be used, with the fallback recorded in the pipeline audit. Creation dates of quantized, republished, or cross-organization weight repositories must not overwrite it. Publishing the built-in catalog requires a valid `YYYY-MM-DD` for every model. Within the same model organization, the UI displays models in a stable order by date descending, then `model_id` ascending.

## Consequences

- Positive: an intermediate user can handwrite the catalog format in ten minutes (gpustack has demonstrated that this format supports an operational catalog of 3770 lines). A single format for internal use, users, and the pipeline eliminates the translation layer and dual formats. The implementation surface for cloning, editing, and YAML import shrinks substantially. A single topology source eliminates divergence between fields and args. Centralized assembly by the server ensures that “the command on the page = the command actually run.”
- Negative/constraints: the product no longer provides evidence browsing or “verified” badges. Credibility shifts entirely to the quality of the catalog production pipeline (the luna/terra/sol pipeline + lint). “Compatibility reference” information (claims without configurations) leaves the product; displayed Chinese GPU coverage depends on complete configurations produced by the research pipeline. Named classes no longer provide Chinese display names, so the UI must derive labels from predicates at runtime (for example, “NVIDIA · CC≥8.9”).
- Deferred items (add only when needed; reserve no structure): value-level gating (mechanical lint mapping flag values → CC thresholds), local_verified, script upload facilities, and three-way readiness classification.
